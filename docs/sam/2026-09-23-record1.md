# 记录文档

## 一、glib 版本要求演变与构建选型依据

> 主题：awesome master 要求 `glib-2.0>=2.79.2`，而 docker-x11base 的 builder（Alpine 3.15 = glib 2.70.5）不满足，需确认该要求从哪个提交/时间点/版本开始，以决定构建容器基础镜像选型。

### 1、引入提交

- **提交**：`179e2b48` — "lib, tests: use GioUnix to use platform-specific Gio classes (#4022)"
- **作者/时间**：Marco Trevisan，2025-10-15
- **原因**（提交说明原文）：新版 GLib 中 `GioUnix` 符号不再从 `GioUnix` 命名空间暴露，lua-lgi 虽能透明处理，但 awesome 改为使用正确命名空间，并顺带把 GLib 依赖升到 2.79.2（"This is the version that provided GioUnix symbols"）
- **改动面**：`awesomeConfig.cmake`（+`glib-2.0>=2.79.2`）+ `lib/awful/spawn.lua` + `tests/_client.lua` + `tests/test-spawn.lua`

### 2、版本对应关系

| awesome 版本 | glib 要求 | 时间 |
|---|---|---|
| **v4.3**（release tag） | `glib-2.0>=2.40` | 2019（从未要求新版） |
| master（#4022 起） | `glib-2.0>=2.79.2` | 2025-10-15（v4.3-1688 之后） |
| 当前 `feat/ai-260923-static` | `glib-2.0>=2.79.2` | v4.3-1754 |

### 3、关键事实

- 全仓库 glib 版本要求只改过 **2 次**：2017-06-02 #1811 引入 `>=2.40`，2025-10-15 #4022 升到 `>=2.79.2`
- `179e2b48` **不在任何 release tag 的祖先里**（`git tag --contains` 为空）——它是 **v4.3 发布后 master 上的提交**，awesome 至今未发新 release
- 因此：**v4.3 用 Alpine 3.15（glib 2.70.5）即可编译**；只有基于 master 的构建需要 Alpine 3.20+（glib 2.80.5，满足 >=2.79.2）

### 4、对构建选型的影响

| 方案 | 说明 | 判定 |
|---|---|---|
| master + Alpine 3.20（glib 2.80.5） | 跟随上游；b16 分析全部基于 master `0a5e50c` | ✅ 当前计划采用 |
| v4.3 + x11base 原 builder（Alpine 3.15，glib 2.70.5） | 可省去 builder 升级，但 v4.3 代码旧、无 shim 分析基础 | ❌ 不采用 |

## 二、回退 glib>=2.40 的风险与可行性评估

> 主题：docker-x11base 原 builder（Alpine 3.15 = glib 2.70.5）不满足 awesome master 的 `glib-2.0>=2.79.2`。若把 master 的 glib 版本要求回退到 `>=2.40`（或直接降到 2.70 可用范围），能否直接复用 x11base 原 builder、省去 Alpine 3.20 升级？本文评估风险与可行性。

### 1、回退的代码面分析

#### 1.1、#4022 到底改了什么（改动全量）

提交 `179e2b48`（2025-10-15，Marco Trevisan）共 4 个文件、14+/12- 行：

| 文件 | 改动 | 性质 |
|------|------|------|
| `awesomeConfig.cmake` | `glib-2.0>=2.40` → `>=2.79.2` | 版本要求（回退点） |
| `lib/awful/spawn.lua` | `Gio.UnixInputStream.new(...)` → `GioUnix.InputStream.new(...)`（2 处） | Lua 命名空间切换 |
| `tests/_client.lua` | `Gio.UnixInput/OutputStream` → `GioUnix.Input/OutputStream`（3 处）+ require | Lua 命名空间切换 |
| `tests/test-spawn.lua` | 同上（3 处）+ require | Lua 命名空间切换 |

**关键结论：这是纯 Lua 层的 GI 命名空间切换，不是 C API 依赖**。C 代码零改动、零风险——master 的 C 层只用到 `g_main_loop_*` / `g_io_channel_*` / `g_timeout_add_seconds` 等 glib 2.40 时代就存在的 API（awesome.c/luaa.c/dbus.c/spawn.c 实测）。

#### 1.2、运行时符号形态（glib 2.70.5 实测）

在 x11base 原 builder（Alpine 3.15 + glib 2.70.5）容器内实测：

| 检查项 | glib 2.70.5 实测结果 |
|--------|---------------------|
| `girepository-1.0/` 中的 typelib | **只有 `Gio-2.0.typelib`，无 `GioUnix-2.0.typelib`** |
| `Gio-2.0.gir` 中的 `UnixInputStream` | **存在**：Gio 命名空间下的 `<class name="UnixInputStream" c:type="GUnixInputStream" glib:type-name="GUnixInputStream">`（5.8MB GIR 中 19 处匹配） |
| `Gio.UnixInputStream`（#4022 前写法） | ✅ 可用 |
| `GioUnix.InputStream`（#4022 后写法） | ❌ require 失败（无 GioUnix typelib） |

**含义**：glib 2.79.2 把 `GioUnix-2.0` typelib 从 `Gio-2.0` 中拆出（这正是 #4022 升版本的原因）；回退后必须**同时**把 3 个 Lua 文件的符号切回 `Gio.UnixInput/OutputStream`。

### 2、回退方案

#### 2.1、方案 A（推荐）：git revert #4022

```bash
git revert --no-commit 179e2b48
```

效果：`awesomeConfig.cmake` 回到 `glib-2.0>=2.40`，3 个 Lua 文件回到 `Gio.UnixInput/OutputStream`。与 #4022 之前的 master 完全等价——那个形态的 awesome 在 glib 2.40~2.79 之间跑了 8 年（2017-2025），Alpine/Ubuntu/Debian 官方包全是这个形态，风险极低。

- 影响面：仅这 4 个文件；LGI 的 `Gio` 命名空间在 glib 2.70 下含 `UnixInputStream` 类 ✅（实测）
- 后续若上游再更新，cherry-pick 冲突点也只有这几个文件，可控

#### 2.2、方案 B：仅改版本号，保留 GioUnix 写法

```cmake
glib-2.0>=2.79.2  →  glib-2.0>=2.40
```

❌ **不可行**：编译期能过（pkg-config 检查），但运行时 `require("lgi").GioUnix` 在 glib 2.70.5 下直接失败（无 typelib），`awful.spawn` 的 stdout/stderr 捕获和测试基建全部崩。方案 B 是伪回退，排除。

### 3、风险清单

| 风险 | 等级 | 说明 | 缓解 |
|------|------|------|------|
| Lua 层符号不匹配 | 高（但已被方案 A 消除） | 只改版本号不动代码 → 运行时崩 | 必须 revert 全部 4 个文件 |
| 上游未来合入依赖 GioUnix 的提交 | 中 | 回退后 master 与上游在 spawn.lua 等文件长期分叉，后续 cherry-pick 可能冲突 | 维护一个"回退补丁"文件，记录与上游差异 |
| lgi 版本对 Gio 命名空间的解析 | 低 | lgi 0.9.2（2018）在 glib 2.70 的 Gio 命名空间下解析 `UnixInputStream` 是 8 年验证过的路径 | 无（b10 已论证 lgi 0.9.2 + 旧 glib 组合是历史主流） |
| 测试基线 | 低 | tests/_client.lua 回到 `Gio.UnixInputStream`，与 2017-2025 的测试形态一致 | 直接跑 T2 spec 基线验证 |
| 与 b16 R6 shim 的关系 | 低 | shim 面向 master 分析，但 GLib/Gio 绑定面（2 函数 + 常量）不受命名空间影响；`GioUnix` 在 b16 8.7 本来就是单列漏项，回退后反而少一个要绑的模块（回到 `Gio.UnixInputStream`） | 8.7 清单按回退后形态更新 |

### 4、结论

- **可行性：高**。方案 A（revert #4022）是 8 年验证过的组合（glib 2.40-2.79 + Gio.UnixInputStream），Alpine/Ubuntu/Debian 官方 awesome 包全在这个形态。
- **收益**：可直接复用 x11base 原 builder（Alpine 3.15 / glib 2.70.5），无需升级 Alpine 3.20；且 x11base 的 `v-pcmanfm` 37.1M 全静态产物正是基于 glib 2.70.5 链出来的，静态配方（`glib-static 2.70.5-r0`）与 b16 二·5.3 完全对上。
- **代价**：与上游 master 在 4 个文件上分叉（截至 2026-09-23，上游 master 在 #4022 之后无相关改动——需定期检查）。
- **建议**：采用方案 A。在 `feat/ai-260923-static` 分支上 revert #4022，并把计划 T1 的 Dockerfile 改回基于 x11base 原 builder 的形态（Alpine 3.15，去掉升级）。

## 四、容器环境调试经验（Alpine 3.15 构建容器）

> 主题：复用 `alpine-builder-gtk224`（Alpine 3.15.10 / glib 2.70.5）作为 R6 构建容器时的环境陷阱与挂载约定。本章是本次调试的教训，直接决定了第三章的结论是否正确。

### 1、容器拓扑

- maki（含 bash 工具）运行在容器内，通过 `DOCKER_HOST=tcp://127.0.0.1:2375` 连内嵌 dind 起构建容器。
- dind 模式挂载无碍：宿主机路径与 maki 容器内路径一致（均在 `/_ext` 下）。**直接挂 `/_ext:/_ext` 一个卷**，容器内路径与宿主机完全一致，免路径转换产生额外认知；`/_ext/tmp`（临时脚本）本就在 `/_ext` 下，一并覆盖。
- 调试期用**长期命名容器**（`docker run -d --name builder-awe --network=host --privileged ...`），跨 `docker exec` 状态持久；**不 commit 镜像、不 push**（infrastlabs 命名空间无写权限，push 实测 `denied`）。

### 2、`--privileged` 陷阱（本次误判的根源）

不加 `--privileged` 时，`apk update` 表现为：只输出一行
`fetch http://mirrors.aliyun.com/alpine/v3.15/main/x86_64/APKINDEX.tar.gz` 之后**无任何错误、无后续行、不处理 community 源**，看似「卡住」。

加 `--privileged` 后 apk 完全正常（索引 v3.15.11，15862 个包，`OK: 15862 distinct packages available`）。

**排查过的非原因**：容器网络（默认 bridge 出网正常，ping 8.8.8.8 通、curl aliyun 200/1.1s）、DNS（114.114.114.114 正常解析）、代理环境变量（无）。

**教训**：`apk search` 在非特权容器返回空 → 误判「Alpine 3.15 没有这些包」。见第三章更正。

### 3、网络与源

- **必须 `--network=host`**：默认 bridge 下容器连自家网关都 ping 不通（`ping 10.18.0.1` 无回包），出网全挂。`--network=host` 后共享 maki 的网络命名空间，`/etc/resolv.conf` 也是 maki 的（114.114.114.114，可用）。
- **容器 egress 会间歇性限流**（环境级，非源问题）：maki 自身 curl 1.1MB/s，容器内曾降到 ~1KB/s（60s 下不完 640KB）。TCP 能连（`nc` 显示 80 open）、ping 通、拿得到 `200 OK`，就是吞吐被掐死；已运行的 ubuntu 容器同样 0 输出 → 影响所有容器。属**会话中途劣化、可自行恢复**，遇到就等一阵重试。
- **镜像源测速**（容器内，640KB APKINDEX，国内源）：

  | 源 | code | 速度 |
  |---|---|---|
  | mirrors.aliyun.com | 200 | 2.55MB/s |
  | mirrors.tencent.com | 200 | 2.50MB/s |
  | mirrors.cloud.tencent.com | 200 | 2.06MB/s |
  | mirrors.huaweicloud.com | 200 | 1.41MB/s |
  | mirror.nju.edu.cn | 200 | 1.34MB/s |
  | mirrors.tuna.tsinghua.edu.cn | 200 | 0.46MB/s |
  | dl-cdn.alpinelinux.org | 200 | 0.05MB/s |
  | mirrors.ustc.edu.cn | 302 | 跳转不可用 |
  | mirrors.{163,sohu,hust} | 404 | 无 v3.15 |
  | mirrors.{zju,sjtu,tencentyun} | FAIL | 不通 |

  不用阿里云时取 **mirrors.tencent.com**（2.50MB/s）。
- **⚠️ 不要用 `apk update --quiet`**：apk-tools 2.12.7 下该标志会**挂死**（无任何输出、不返回）；去掉 `--quiet` 用正常输出则秒完（`OK: 15862 distinct packages available`）。曾误判为网络/特权问题，排查了一轮。
- **`docker exec` 会被后台进程卡住**：脚本里 `cmd &` 起的后台进程继承了 stdout/stderr 的文件描述符，`docker exec` 会等 FD 关闭而不返回（脚本实际已跑完但 exec 不退出）。诊断脚本把输出重定向到文件、不要用管道，也不要后台化命令。
- 容器内 **github.com 被拦**：`git clone https://github.com/...` 报 `could not read Username for 'https://github.com': No such device or address`。
- **gitee 可用**（200 / 1.2s，需 egress 正常时），源码一律走 `gitee.com/g-system/...` 镜像，与 x11base 现有约定一致（如 `compile/src/v-tint2/build.sh:70,86,111`）。

### 4、挂载约定

```
docker run -d --name builder-awe --network=host --privileged \
  -v /_ext:/_ext \
  registry.cn-shenzhen.aliyuncs.com/infrastlabs/x11-base:alpine-builder-gtk224 \
  bash -c 'while :; do sleep 3600; done'
```

**只挂 `/_ext` 一个卷**：工作目录和临时脚本目录都在 `/_ext` 下，一个卷全覆盖，容器内路径与宿主机完全一致。不要拆成 `-v /_ext/home/headless/xm-zs01:/work -v /_ext/tmp:/root`——额外路径转换徒增认知成本。

容器内可用路径（与宿主机一致）：
- `/_ext/home/headless/xm-zs01/fk-awesomewm` — awesome 源码

### 7、教训清单

1. **apk 静默失败会污染所有依赖结论**——`apk search` 空结果不等于「仓库没有」。先确认 `apk update` 真成功（看到 `OK: N distinct packages available`）再做存在性判断。
2. **pc 名 ≠ apk 包名**：`xcb-util-wm-dev` 提供 `xcb-icccm.pc`/`xcb-ewmh.pc`；校验依赖要用 `pkg-config --modversion <pc名>` 逐个核对。
3. **`--rm` 容器里的安装不留存**：`docker run --rm` 跑完即丢，`docker commit` 前容器必须已 `--rm` 掉会失败（`No such container`）。
4. **bash 工具 stdout 常被吞**：关键输出重定向到挂载卷文件再 `cat`（如 `> /root/out.txt`）。
5. **改环境前先看 x11base**：20 多个组件构建脚本已覆盖大部分依赖，直接复用不抄代码。
6. **别把慢下载当挂死**：先确认 `apk update` 真成功（`OK: N distinct packages`）、curl 带 `-w speed_download` 看真实吞吐，再下结论。这次「apk 卡住」连错三轮：先误判为 `--privileged` 缺失，后误判为网络不通，再误判为 egress 限流，真因还包括 `apk update --quiet` 本身会挂死。
7. **挂载少即是多**：`-v /_ext:/_ext` 一个卷即可，容器内路径与宿主机一致；多拆挂载会产生两套路径要记住。
8. **输出不要走管道**：apk 用 `\r` 刷进度，`| head`/`| tail` 会把输出吃成无输出（曾反复误判为命令失败）；直接重定向到文件。
9. **脚本里不要后台化命令**：`cmd &` 会拖住 `docker exec` 不返回（继承的 FD 不关闭），诊断脚本容易卡死在看不见的地方。

#### 6.7、方法论陷阱

1. **`pkg-config --static --exists` 不可靠**：只校验 `Requires.private` 的 pc 能否解析，**从不检查 `.a` 是否存在**。dbus-1（`Libs.private:` 为空）与 xkbcommon 都会误判 OK。判静态可行性必须直接 `ls *.a`
2. **Alpine 命名/路径 ≠ Ubuntu**：`libpango-1.0.a`（非 `libpango.a`）、`liblua-5.3.so.0`、dbus 头在 `/usr/include/dbus-1.0/`（非 `dbus-1`）、`/lib/libz.a`；pc 名 `x11`（无 `libx11.pc`）、`xcb-icccm`（无 `libxcb-icccm.pc`）、`libstartup-notification-1.0`
3. **`glib-2.0-unix.pc` 不存在**，但 `glib-unix.h` 在主 glib 头目录内，可直接编译，且不在 `AWESOME_DEPENDENCIES` 中，非阻塞
4. **诊断脚本漏 `docker exec` 会跑在宿主机上**，全报假 MISS（判别特征：pkg-config 与 apk 同时全失效）
5. **容器内 `find /` 会遍历 `/_ext` 绑定挂载（宿主机整盘）挂死**，exec 超时并把后续输出吞光
6. **`ls /usr/local/include/lua*` 匹不上 `lauxlib.h`**：`lauxlib` 不匹配 `lua*` glob，会误判头文件缺失；用 `ls /usr/local/include/lua* /usr/local/include/lauxlib.h` 或 `ls /usr/local/include/ | grep -i lua`

| B 混合链接 | 保留 `libdbus-1.so` 作为唯一动态依赖 | 打折 R6「去动态依赖」目标，而 A 已验证可行 |
| C 源码条件化 | 把 awesome 的 D-Bus/SNI 分支 `#ifdef` 掉（约 2 个文件：`main.c`、`sni.c`） | 需背 fork 差异并维护 rebase，代价高于 A |

**Lua 5.3 静态库 —— 已解决（选路线 A 源码静态编译）**

原阻塞点与选型：

- 无 `lua5.3-static` 包，`lua5.3-dev` 不带 `.a`，x11base 全库无现成脚本 → apk 与 x11base 两条路都不通
- awesomeConfig.cmake 里的 `-llua` 目标名字，与 Lua 源码的 `liblua.a`（无版本后缀）**天然对齐**；apk 装的是 `liblua-5.3.so.0`（运行时版），静态名根本不同 → 静态链接必须自建
- **`luaL_openlibs` 在 `lualib.h`，不在 `lauxlib.h`**：源码里的辅助库头文件是 `lauxlib.h`，但它不声明 `luaL_openlibs`。测试代码若只 include `lauxlib.h` 会报 "implicit declaration"，需同时 include `lualib.h`。库符号 `nm liblua.a` 明确可见 `T luaL_openlibs`，无缺失

**关键前提实测成立**：Lua 5.3.6 能脱离 readline 完成静态库构建。

- 源码：官方 tarball `lua-5.3.6.tar.gz`（`www.lua.org/ftp/` 直下）
- 构建：`make generic MYCFLAGS="-fPIC" MYLDFLAGS="-DLUA_USE_POSIX" MYLIBS="-lm"`
- 关键差异 vs `make linux`：`linux` target 会顺带编 `lua` / `luac` 解释器，需要 `readline-dev`；容器未装 → 解释器失败。**但 `make generic` 是纯 core 库 target，不需要 readline**
- `.pc` 文件：Lua 源码的 `make install` **不生成** `.pc`，手写 `/usr/local/lib/pkgconfig/lua5.3.pc`，`Libs` 显式带 `-lm`（不带会缺 libm 符号）
- 头文件路径：装到 `/usr/local/include/`（不是 `include/lua5.3/`，源码不带版本子目录），静态编译时 `-I/usr/local/include` 优先，避免和 apk 的 `.so` 版混淆
- **决定性验证**：`gcc -static -o /tmp/t_lua /tmp/t_lua.c -L/usr/local/lib -llua -lm` → `ldd` 报 `Not a valid dynamic program` → 运行输出 `Lua 5.3`
- 产物：`/usr/local/lib/liblua.a`（464KB）+ `pkgconfig/lua5.3.pc`（`Version: 5.3.6`）+ `include/{lua,lauxlib,lualib,luaconf}.h + lua.hpp`
- 已固化进 `docs/sam/scripts/03-container-build-static-libs.sh` 第 4 步（含静态链接冒烟）

- 脚本名**直接体现要干的事**，相关联的事合进同一脚本，不做"一件小事一个脚本"

### 3、关键手法

**`-Wl,--start-group / -Wl,--end-group` 包裹整个库表。** 前几轮靠加库 + 手工排序只能把符号数从 238 降到 20，剩余 20 个全部是**静态库单向扫描顺序问题**（如 `-lexpat` 排在 `-lgio-2.0` 之前）。group 让 `ld` 反复扫描至符号收敛，一次归零。

### 4、调试过程与核心 bug（20:30–21:10）

本轮约 50% 时间花在 metatable / 栈操作 bug 上，Lua 5.3 C API 的隐式栈语义是主因。

| # | 现场 | 根因 | 修复 | 时间 |
|---|------|------|------|------|
| 1 | 冒烟第一次跑就 segfault（`attempt to index nil value`） | `class_setup` 里 `lua_setfield(L, LUA_REGISTRYINDEX, REG_CLASSES)` 把新表**弹走**，后面 `lua_rawseti(L, -2, cls)` 把 clsinfo 写到了 module table 而不是 REG_CLASSES，`lua_pop(1)` 又把 module 丢光 | `setfield` 后立即 `lua_getfield(L, LUA_REGISTRYINDEX, REG_CLASSES)` 补回引用 | 20:52 |
| 2 | `Pango.Color.new()` 返回 `function` 类型而不是 userdata | `push_obj` 里在 `luaL_setmetatable` 之后**又**调 `lua_setmetatable(L, -2)`——`luaL_setmetatable` 宏已把栈顶弹走（它展开为 `luaL_getmetatable, lua_setmetatable(L, -2)`），第二个 `setmetatable` 拿到的 `-2` 是错的引用 | 删除第二行；`luaL_setmetatable` 已经消费栈顶 | 20:58 |
| 3 | `c.red` / `c.green` / `c.blue` 返回同一个 table 指针 | `m_index` 里 `lua_call(L, 1, 1)` 把 result 推到 slot 6，然后 `lua_settop(L, 3)` 保留的是 slot 3 的 **`REG_CLASSES`**，不是 result | 改用 `lua_replace(L, 3)` 把 result 直接挪到 slot 3 后再 `settop(3)` | 21:03 |
| 4 | GC 时 `GLib-GObject-CRITICAL: g_object_unref: assertion 'G_IS_OBJECT (object)' failed` | `PangoFontDescription` 和 `PangoFontMetrics` 都是 **GBoxed**（独立 refcount），不是 GObject；错传 `d_unref` 触发 GLib 断言 | 新增 `d_fontdesc`（→ `pango_font_description_free`）和 `d_metrics`（→ `pango_font_metrics_unref`） | 21:08 |
| 5 | `cx_get_font_description` 的返回对象在 context 析构时被二次释放 | context 拥有 fontdesc，取出的是**借引用**，不应在 Lua 侧释放 | `cx_get_font_description` 改用 `d_noop` | 21:10 |

**共性教训：** Lua 5.3 C API 对「宏消费栈顶」和「显式 pop」的语义不一致。`luaL_setmetatable` 是宏，`lua_setmetatable` 是函数；两者都不能用「栈位置数字」去推理，得看源码。类似地，`lua_setfield` 到 `LUA_REGISTRYINDEX` 也是 pop 语义。GLib 对象家族里 `PangoFontDescription` / `PangoFontMetrics` 是罕见的 GBoxed（不是 GObject），必须用它们自己的 free/unref 而不是 `g_object_unref`。

### 7、版本不匹配处理（Pango 1.48 vs 1.50）（22:30）

lib/ 代码是照 Pango 1.50+ API 写的，但容器里装的是 Pango 1.48。shim 必须在两个版本之间做桥接。处理策略分三层：

**1、编译期分支（`#if PANGO_VERSION_*` 宏）**

只有一处：`d_metrics` 里的函数改名。

```c
#if PANGO_VERSION_MAJOR * 100 + PANGO_VERSION_MINOR >= 150
    pango_font_metrics_free(p);   // 1.50+ 改名，metrics 从 refcounted 变 copy
#else
    pango_font_metrics_unref(p);  // 1.48
#endif
```

**2、运行期 workaround（在函数体里绕开缺失 API）**

- **`cx_set_resolution`**：1.48 没有 `pango_context_set_resolution`（1.50 才加，resolution 位置变了）。走 font map 路径：`pango_cairo_font_map_set_resolution(...)` + `pango_context_changed(c)` 通知所有 layout 刷新。
- **enum 序列化**：真实 Pango 的 enum 是 C int，lgi 包装成字符串。shim 用 `enum_from`/`enum_to` 手写映射，UPPERCASE variant 名（`"LEFT"` / `"WORD_CHAR"` / `"END"` / `"CENTER"`）。因为 `wibox/widget/textbox.lua` 用 getter 结果与 setter 入参直接 `==` 比较——两端名字必须完全对齐。

**3、未实现（记在文件头注释里，明确标为「本轮不做」）**

| 缺失 API | 归属 | 处置 |
|----------|------|------|
| `pango_layout_get_preferred_size` / `_at_dpi` | 1.50+ | **不做**。`lib/` 只通过 `wibox/container/place.lua` 间接碰，本次冒烟路径够不着。将来做可基于 `pango_layout_get_extents()` 重实现 |
| `pango_layout_get_height_for_width` / `_at_dpi` | 1.50+ | 同上 |
| `c.alpha` 属性 | 1.50+ 只有 `pango_color_parse_with_alpha`，没有 alpha 字段 | **故意留 nil**，语义与「任何缺失属性」一致，color.lua 只读 red/green/blue |

**4、`PangoColor` 结构布局差异**

- **1.48**：`PangoColor` 是公开 struct，`red/green/blue` 可直接读，无 accessor
- **1.50+**：变成 opaque，得走 `pango_color_get_red()` 等

shim 直接读字段：`lua_pushinteger(L, ((PangoColor *)chk(L, 1))->red)`。**这是硬编码 1.48 语义的**——迁到 1.50 时这里得改，但没有 `#if` 保护，属于「未来工作」。文件头注释明说了这点。

**`PANGO_ATTR_LANGUAGE` 自动注入**：真实 Pango 和 LGI 都不做，测试脚本原来误以为 LGI 做了 → 已改测试期望。shim 跟真 Pango 对齐，**不**跟 LGI 的非标准包装层对齐。

#### 4.3 cairo 语义核查（D.3，b16 一·8.5）

目标：核对 b16 一·3.1 关于 cairo shim「隐蔽坑」的描述，估算 Phase 2 Cairo 层人天。

- **56 方法 / 19 静态构造器**（`cairo.Context` 35 次、`cairo.Operator` 33 次、`cairo.ImageSurface` 31 次、`cairo.Format` 25 次、`cairo.Pattern` 20 次 …）。
- **oocairo 覆盖：47 / 56 ≈ 84%**（数量口径）。
- **关键修正：** b16 一·3.1 描述的「`__typename` 字段必需，否则 `_to_surface` 静默失败」**是伪命题**：
  - `lib/` 全量 `__typename` 出现次数 = **0**
  - 真正的类型判定靠 `Xxx:is_type_of(obj)` 元方法（**9 处**，分布在 `surface.lua:2` / `color.lua:2` / `wallpaper.lua:2` / `imagebox.lua:3`）

- **含义：** shim 必须实现 `is_type_of(self, other)` 元方法，而不是只塞 `__typename` 字段。`__typename` 依然建议保留（b16 一·2 L73-80 要求），但决定「静默失败还是画出来」的是 `is_type_of`。**风险等级从「中（排查成本最高）」下调到「低」**。
- **4 个特殊点（Phase 2 主要成本来源）：**
  1. `is_type_of` 元方法（9 处，**不是** `__typename`）
