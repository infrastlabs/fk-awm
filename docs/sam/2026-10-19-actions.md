## 一、出包 Actions 方案与清单

### 1、参考 x11base 模式

来源：`/_ext/home/headless/xm-zs01/docker-x11base/.github/workflows/docker-image-x11-base.yml` + `compile/buildx.sh`

- `runs-on: ubuntu-22.04` 单 job；`setup-qemu-action`（platforms: arm,arm64,…）；
  `setup-buildx-action`（driver `network=host`）。
- `buildx.sh` 约定：`plat="--platform linux/amd64,linux/arm64,linux/arm"` 多架构一次
  buildx；registry 缓存 `--cache-from/--cache-to type=registry`（QEMU 慢的兜底）；
  `--provenance=false`。
- 多仓库推送（dockerhub/ali/tencent/qingcloud，secrets）。
- 产物落 `.github/workflows/.ws/pkgs/`；release 用 `softprops/action-gh-release`
  attach `pkgs/*-*.tar.gz`（arch-后缀命名防冲突）。

### 2、方案定调（用户拍板）

- **不再新建 builder 镜像**：直接用现成 `infrastlabs/x11-base:alpine-builder-gtk224`
  （registry 上三架构都有，`docker run --platform linux/{amd64,arm64,arm}` 自动拉对应
  digest）。
- apk 缺的依赖：出包准备时在容器内直接 `apk add`。
- 需源码编译的库（librsvg/libcroco 等）：容器内现编。
- 环境准备复用**仓库内已提交脚本**：`02-container-install-deps.sh`（apk 依赖）、
  `03-container-build-static-libs.sh`（源编 .a）——CI 只做编排，不改逻辑。

### 3、环境准备清单（gtk224 三架构镜像）

> Alpine 版本三架构同版本（用户确认），包名一致；但 02 的 apk 清单开工时仍需核对。

#### 3.1、apk 基础工具

| 项 | 包 | 备注 |
|---|---|---|
| 构建链 | `git cmake ninja build-base file tar awk bash` | 11-script preflight 硬查，缺少即退 |
| Lua | `lua5.3` + `lua-libs` | 必须 `/usr/bin/lua5.3` 可跑 |
| pkg-config | `pkgconf` + `pangocairo-static-dev` | preflight 用 pkg-config 查 |

#### 3.2、静态依赖闭包 .a

| 组 | 包（-static-dev） |
|---|---|
| Lua/工具 | `lua-static-dev libtool-static-dev` |
| X | `libX11 libXcursor libXrandr libXi libXinerama libxcb libXext xcb-util xcb-util-image xcb-util-keysyms xcb-util-wm xcb-util-renderutil xcb-util-xrm` |
| 图形 | `cairo pangocairo pixman png freetype harfbuzz harfbuzz-icu icu` |
| 系统 | `glib gio dbus wayland wayland-protocols libudev xdg-basedir zlib` |

> ⚠️ 装 -dev（只有 .so）ninja 报 cannot find -lpango；preflight 逐个找 .a 兜底。

#### 3.3、源码现编库

| 库 | 版本 | 配方 |
|---|---|---|
| libcroco | 0.6.13 | x11base `v-tint2/build.sh libcroco`（STATIC=yes，gitee 镜像 fk-libcroco） |
| librsvg | 2.40.21 | x11base `v-tint2/build.sh librsvg`（STATIC=yes，fk-librsvg） |
| 前置 | `libxml2-static expat` + `autoconf automake libtool` | autogen 需要 |

#### 3.4、可选

| 项 | 说明 |
|---|---|
| `upx` | armv7 可用（参考 x11base）；缺则 step4 自动跳过压缩 |
| `Xvnc`（`tigervnc` 包；`builder-awe` 仓库里 **没有** tigervnc，现用的是外部拷进来的静态版） | 仅 SMOKE=1 冒烟需要；CI 默认 SMOKE=0。**比 Xvfb 多两个前置**：`xkeyboard-config`（提供 `/usr/share/X11/xkb`，**必须在这个路径**；`xkbcomp` 是另一个包，两者分开装）——缺则 Xvnc 起不来（`XKB rules file` 找不到 → `Failed to activate virtual core keyboard`）。启动命令也不同：`Xvnc -ac -localhost yes :N -geometry 1280x800 -depth 24`（Xvnc 没有 Xvfb 的 `-screen 0 WxHxD`） |

#### 3.5、每架构差异注意

| 架构 | 要点 |
|---|---|
| amd64 | native，最快 |
| arm64 | QEMU 模拟 |
| armv7 | armhf 32 位；`--platform linux/arm` 自动拉对应 digest；UPX 用 armv7 版（x11base 法） |

#### 3.6、CI 脚本侧准备

| 项 | 说明 |
|---|---|
| `fetch-depth: 0` | 容器内 `git describe` 版本号要全历史 |
| `.ws/pkgs` 挂载 | 产物落 `.github/workflows/.ws/pkgs/awm-static-musl-<arch>-*.tar.gz` |
| arch 注入包名 | x11base arch-后缀命名法 |
| 时间戳/时区 | 11-script 已内建 `TZ=UTC-8` |

### 4、脚本复用映射与缺口

| 清单类 | 对应脚本 | 覆盖 |
|---|---|---|
| A+B 大部分 | `02-container-install-deps.sh` | apk（lua/xcb/glib/cairo/pcre/expat/zlib/freetype/fontconfig/png/jpeg/xkbcommon/dbus/lxdg/startup-notification）+ 22 pc + 18 .a 校验 + icccm/ewmh 编译冒烟；幂等（有 libglib-2.0.a 即 skip） |
| C 部分 | `03-container-build-static-libs.sh` | 源编 xcb-util（x11base v-tint2）/ xdg-basedir / dbus / lua |
| rsvg/croco | 缺口 | 走 `v-tint2/build.sh libcroco + librsvg`（02/03 未含） |

**02 是 v3.15 时代旧清单，比当前 11-script 链接闭包缺**：`cmake ninja build-base file tar awk bash`
（3.1）、`pangocairo pango* harfbuzz-static pixman-static brotli-static icu-static`
（3.2）、`libxml2-static + autoconf automake libtool`（3.3 前置）、`upx/Xvnc`（3.4）。
若补 3.4，除 `tigervnc` 外还须一并补 `xkeyboard-config` + `xkbcomp`，缺任一个 Xvnc 都起不来。

### 5、落地方式（不改脚本逻辑）

每架构 job：

```
docker run --platform linux/<arch> \
  -v $repo -v .github/workflows/.ws \
  gtk224 bash -c '
    02-container-install-deps.sh [--force 按需]
    03-container-build-static-libs.sh
    v-tint2 build.sh libcroco; v-tint2 build.sh librsvg
    <补 3.1-3.4 缺口项：apk add ...>
    11-package-static-release.sh all
  '
```

产物 → `.ws/pkgs/` → `upload-artifact` / release attach。

### 6、实施顺序与风险

1. **先 x64 打通全链路**（workflow + prep 编排 + 产物/发布）。
2. **再 arm64/armv7**——开工前需评估/验证两点：
   - **环境依赖差异**：三架构 gtk224 的 apk 包名/静态库是否与 x64 一致；
     armv7 32 位下的 `-static-dev` 闭包是否存在缺包。
   - **awe 编译差异**：librsvg/libcroco 在 arm/armv7 下 configure/make 行为
     （x64 已验证的配方是否原样成立）、UPX armv7 压缩、CMake 链接闭包在
     32 位下的告警/缺失符号。

#### 1.4、B/C 验证结果（2026-10-19）

**B. 三架构镜像存在性 ✅**

`docker manifest inspect` 因 aliyun registry 认证问题拿不到，改用 registry HTTP
API（匿名 token + `Accept: application/vnd.oci.image.index.v1+json`）查
`infrastlabs/x11-base:alpine-builder-gtk224` 的 OCI index：

| 平台 | 架构 | digest(前 24) |
|---|---|---|
| linux | amd64 | sha256:14e6cbede368ac2e02… |
| linux | arm64 | sha256:dd4cf263fe732e1c44… |
| linux | arm(v7) | sha256:a8fd6026cc624e7e99… |

- ✅ **三架构齐全**，与 §2 声称一致。
- 另有 3 个 `unknown/unknown` 条目（digest 8b096451…/1adcf8b1…/34ed474a…）——
  经逐 digest 查询，registry 报 **UNKNOWN**（OSS driver 层找不到 manifest blob），
  **是孤儿死条目，不影响三架构拉取**。
- 🔶 查询命令备忘（aliyun 认证头）：先向
  `https://dockerauth.cn-hangzhou.aliyuncs.com/auth?service=registry.aliyuncs.com%3Acn-shenzhen%3A26842&scope=repository%3Ainfrastlabs%2Fx11-base%3Apull`
  拿 token，再带 `Authorization: Bearer` 查 index。

**C. v-tint2/build.sh 架构敏感性 ✅**

- `libcroco`/`librsvg` 两函数都是纯 autotools 配方：
  `git clone gitee → ./autogen.sh → ./configure --enable-static [--disable-shared] → make → make install
  （STATIC 模式 rm -f .so 保留 .la）`。
- 全文件 346 行 scan：仅 1 处注释提到 arm64，**无任何 -march/-m32/-m64/asm/SIMD
  等架构硬编码**。
- QEMU 下是「模拟 native 编译」（configure 检测的就是 arm 环境本身），
  **x64 配方可原样用于 arm64/armv7**——§6.2「awe 编译差异」风险主要收敛到
  UPX armv7 与 CMake 32 位链接告警，配方本身不背锅。

**⚠️ 02 脚本 latent bug：`pcre-static` 不存在（2026-10-20 实测）**

`02-container-install-deps.sh --force` 在 v3.15 源 **FATAL**（全新容器 CI 首跑必踩）：

```
ERROR: unable to select packages:
  pcre-static (no such package):
    required by: world[pcre-static]
FATAL apk add
rc=1
```

- 根因：v3.15 仓库**没有** `pcre-static` 包；正确包名是 **`pcre-dev`**

- 为什么之前没炸：02 幂等 skip（检测到 `libglib-2.0.a` 即跳过 apk），
  builder-awe 里 .a 是历史装好的，apk add 分支长期未真正执行。
- 修复：`pcre-static` → `pcre-dev`；`apk add --simulate` 全绿（含 pcre-dev 替换后）。
- ✅ **已修已验**（2026-10-20，commit `cdd64b12b`）：02 脚本 `pcre-static` → `pcre-dev`，
  提交后重跑 `02 --force` → `ALL GREEN, 缺失总数 0`（含 22 pc + 18 .a 校验 +
  ICCCm+EWMH 编译冒烟全过）。

**它是什么 + awesome 源码哪里用到（2026-10-20 核实）**：

- libxdg-basedir 是一个实现 **XDG Base Directory 规范**的 C 库（提供
  `xdgInitHandle/xdgSearchableConfigDirectories/xdgConfigHome` 等函数），
  awesome 编译链的硬依赖（`awesome.c`/`luaa.c` 直接调用，非可选）。
- **用途：rc.lua 配置文件的 XDG 标准查找路径**，在 awesome 启动流程 `awesome.c`：
  1. `awesome.c:603` `xdgInitHandle(&xdg)` —— 初始化 xdg 句柄
     （读 `$XDG_CONFIG_HOME`/`$XDG_CONFIG_DIRS`）；
  2. `awesome.c:607` `xdgSearchableConfigDirectories(&xdg)` —— 取 XDG 配置目录列表
     （`~/.config`、`/etc/xdg` 等），**逐个拼 `/awesome` 后缀**进 rc.lua 搜索路径；
  3. `awesome.c:624/651/855` `luaA_find_config(&xdg,...)`/`luaA_parserc(&xdg,...)`
     —— 用 xdg 句柄定位并解析生效的 rc.lua。
- **一句话**：awesome 靠它实现「配置文件按 XDG 规范查找」——`~/.config/awesome/rc.lua`
  优先、`/etc/xdg/awesome/rc.lua` 兜底；没有它 awesome 找不到 rc.lua
  （`xdgInitHandle` 失败直接 `fatal`）。故链接闭包必须带 `libxdg-basedir.a`。
- 静态闭包原因：Alpine 只有 `libxdg-basedir-dev`（.so），无静态包 →
  源码 `--disable-shared --enable-static` 编 `.a`（约 97KB）。

  若 `$ROOTFS/rootfs/usr/local/static/awm` 存在且 `linux_$arch` 无则用根目录（amd64 时）。
- 验证：真实 undock 拉 awm 镜像（OCI manifest, platform:{}）→ 展开 `rootfs/usr/local/static/awm`；
