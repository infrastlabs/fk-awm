## 一、Phase 2 起步决策（2026-09-24 01:13–01:30）

> 主题：把 Spike 3 D.5 决策「调整 R6」落到具体施工。第一个决策：Cairo shim 是否复用 oocairo。
>
> **时间轴：** 01:13 拉起 cairo shim 设计文档 → 01:17 复核 Spike 3 D.3 与 D.5 → 01:20 定「不复用 oocairo」→ 01:24 拆分 4 部分串行施工 → 01:30 收官并挂 monitor 26。

### 1、原始 Spike 3 D.3 决策（复用 oocairo）

Spike 3 D.3 的原始方向是「拿 oocairo 当 shim 底层、lib/ 侧套一层 LGI 语义」。数据如下：

| 项 | 值 |
|---|---|
| oocairo 覆盖 | 47/56 方法（~84%，`spike3-cairo-semantics.md` §5） |
| shim 4 特殊点 | is_type_of 元方法 / enum→string 常量代理 / __newindex 拦截 / show_layout Pango 桥接 |
| 估算人天 | 2.5-3 |

D.3 认为「oocairo 数量覆盖 84% + 4 个特殊点补齐 = 2.5-3 人天」是划算路径。Spike 3 D.5 综合决策采纳了这个数字，写进了 Phase 2 剩余 8 项施工清单的「Cairo 层 2.5-3 人天」档。

### 2、当前决策：不复用，写自己的（2026-09-24 01:20）

**原因：**

1. **oocairo 在容器里没装**（`pkg-config oocairo` 未找到，Alpine 3.15 仓库无此包）。要么源码构建 oocairo（另一个 12+ 年老项目，autotools），要么放弃 oocairo——两条路都不是「省事」路径。
2. **oocairo 是 12+ 年老手写绑定**（awesomeWM 官方，2011-2014 最后活跃），模块名 `Ctx/Surface` 而不是 LGI 惯例的 `Cairo.Context/Cairo.Surface`。lib/ 侧 35 处 `cairo.Context(...)` 静态构造调用（`spike3-cairo-semantics.md` §1）全部依赖 `Cairo.*` 命名空间，套 oocairo 需要再加一层别名层。
3. **oocairo 无 `._native` / `is_type_of` / `__gc` 幂等**——这些是 lib/ 硬需求（10 处 `._native` + 9 处 `is_type_of`，`spike3-lgi-api-inventory.md`）。oocairo 的对象是纯 Lua table 包装，裸指针通道和幂等释放这两条它都给不了。
4. **oocairo 对象模型是纯 Lua 包装**（不是 full userdata + destroy callback），与 `lgishim_pango.c` 的 wrap struct 模式（`typedef struct { void *p; void (*destroy)(void*); int cls; } wrap;`）不兼容。混用会引入两套对象模型，`m_index` / `m_gc` / `push_obj` 都要写两份。
5. **复用净收益接近 0**：oocairo 提供的 `cr:move_to(x, y)` 这种纯 C API 包装，自己写也就 5 行，比包装 oocairo 的 `Ctx.MoveTo(cr, x, y)`（函数式调用，cr 还得先转 full userdata）还简单。

**结论：写 `lib/vendor/lgishim_cairo.c` 独立 shim**，沿用 `lgishim_pango.c` 的 wrap struct + metatable 模式，静态链接 `-lcairo`（已在 `CMakeLists.txt:141` 的 `AWESOME_REQUIRED_LDFLAGS`）。

### 3、关键洞察：复用不到什么东西

对比表：

| 需求 | oocairo 提供？ | 自己写成本 |
|------|:-------------:|:----------:|
| wrap struct + destroy callback | ✗ | 30 行 |
| ._native / :finish() / __gc / is_type_of | ✗ | 60 行 |
| cr.status 返回字符串 | ✗（返回整数） | 10 行 |
| enum 常量表 | ✗ | 100 行 |
| __newindex 拦截 5 属性 | ✗ | 40 行 |
| cr:move_to / line_to 等 56 方法 | ✓ | 每方法 5 行 = 280 行 |
| cr:set_source(pattern) 跨对象 | ✓ | 已含上表 |
| cr:show_layout(Pango Layout) | ✗ | 20 行 |
| **合计** | | **~540 行** |

自己写 540 行 C 比包装 oocairo 多写 300 行，但换来：

- **静态链接干净**（不用 build oocairo，不引 `liboocairo.so`）
- **与 lgishim_pango 同手法**（wrap struct + metatable 模式完全复用，`getud`/`chk`/`push_obj`/`class_setup` 等 helper 直接复制）
- **无额外依赖**（CMake 里 `-lcairo` 已经通过 pangocairo 的 Cflags 拉进头路径，不用新增 `pkg_check_modules(cairo)`）
- **与 Pango shim 一样规避已修的 6 个 bug**（Spike 2 修过的 `is_type_of` 语义 / `attributes=nil` / `metrics` 单位 / `font` 单位 / `finish` 前后值，写法已经踩过一遍坑，Cairo shim 直接照搬正确姿势）
- **命名对齐 LGI 惯例**（`Cairo.Context` / `Cairo.Surface` / `Cairo.Pattern`，lib/ 侧 35 处 `cairo.Context(...)` 调用零改动）

**净结论：** oocairo 的 84% 数量覆盖率里，真正「复用不写」的核心是 47 个 `cr:xxx()` 方法，每个 5 行 = 235 行；剩下 5 个特殊方法 + 属性 getter/setter + shim 元方法（`._native`/`:finish()`/`is_type_of`/`__newindex` 拦截/enum 常量表/`cr.status`）共 265 行，oocairo 一条都给不了。所以「复用」在净代码量上只是 235 行 vs 280 行的差，但在依赖、静态链接、对象模型一致性上全是净收益。

### 2、冒烟暴露的 5 个真实 C 层 Bug

Part 2 冒烟首跑时连续触发 5 个 bug，逐个定位修复。本节记录症状、根因与修法。

#### Bug 1：`class_call` 索引用错

**症状：** `cairo.Rectangle{...}` 报 `attempt to call a table value`；`SetOperator()` / `set_filter()` 行为错乱（调的不是 `new` 而是第一个实参）。

**根因：** `class_call` 原写 `lua_call(L, lua_gettop(L)-2, 1)`。`lua_call(L, nargs, nresults)` 调用的是栈上 `top - nargs` 位置的函数——这意味着它调的是栈底第二个值（第一个实参），而非类表的 `new` 方法。0 参构造器恰好能工作，因为此时 `self` 就在那个槽位，但 1+ 参数时必错。

**修法：** 显式取 `new` 再调：
```c
lua_getfield(L, 1, "new");
lua_insert(L, 2);
lua_remove(L, 1);
lua_call(L, lua_gettop(L)-1, 1);
```
关键语义：`lua_call` 要求被调函数紧贴在所有实参**之上**，即 `[func, arg1, arg2, ...]` 布局。`lua_insert(L,2)` 把 `new` 移到 `self` 之上、实参之下，`lua_remove(L,1)` 删掉原类表，栈变成 `[func, arg1, ...]` 标准调用布局。

#### Bug 2：`m_index` 属性设置器查找时的栈纪律

**症状：** 访问属性（如 `cr.matrix` / `cr.font_size`）时 `attempt to index a nil value`。

**根因：** 新增"属性设置器"查找路径后，代码在尝试 `lua_getfield(L, -1, "p")` 时，`-1` 槽位仍是方法表而非类信息表——因为未在查 `p` 之前弹出 `m` 表和 value。栈上多出两层，`-1` 指向了错误的对象。

**修法：** 查 `p` 之前先 `lua_pop(L, 2)`（弹出方法表 + 对应 value），再走属性解析。

#### Bug 3：Matrix 按指针返回的 use-after-free

**症状：** `Matrix:invert()` 返回的矩阵里 `xx` 读到 `4.94e-324`（垃圾值）。同样影响 `matrix_mul`、`ctx_get_matrix`、`pattern_get_matrix`。

**根因：** 这四个 getter 函数内部声明了栈局部 `cairo_matrix_t m`，取 `cairo_matrix_t *p = &m`，再把指针包进 userdata 返回给 Lua。Lua GC 触发 `free()` 时释放的是**栈地址**——该栈帧早已归还，栈内存被后续调用覆盖，读到随机残留值。

**修法：** 新增 `push_matrix()` 堆拷贝助手：
```c
static void push_matrix(lua_State *L, const cairo_matrix_t *src) {
    cairo_matrix_t *m = lua_newuserdata(L, sizeof(cairo_matrix_t));
    *m = *src;
    // 设置 metatable 等...
}
```
四个 getter 全部改用 `push_matrix()`，GC 释放的是堆地址，不再访问已销毁栈帧。

#### Bug 4：`ctx_reset_matrix` 传 NULL

**症状：** `cr:reset_matrix()` 触发 SIGSEGV。

**根因：** 原实现调用 `cairo_set_matrix(cr, NULL)`。此容器 cairo 1.16.0 里 `cairo_set_matrix` 会对 NULL 参数解引用（它内部无条件 `cairo_matrix_multiply(&tmp, &cr->gstate->ctm, matrix)`，NULL `matrix` 直接段错误）。

**修法：** 传显式单位阵：
```c
cairo_matrix_t id;
cairo_matrix_init_identity(&id);
cairo_set_matrix(cr, &id);
```

#### Bug 5：`ctx_get_source` / `ctx_get_target` 用错销毁回调

**症状：** GC 时 abort：`Assertion failed: CAIRO_REFERENCE_COUNT_HAS_REFERENCE`。

**根因：** `cairo_get_source()` 和 `cairo_get_target()` 返回的是**借用指针**（不增 refcount）。但 shim 在 `push_obj` 时用了 `d_pattern` / `d_surface` 作为 destroy 回调——即 Lua GC 时对借用指针调了 `cairo_pattern_destroy()` / `cairo_surface_destroy()`，refcount 被多减一次触发断言。

**修法：** 两处都改用 `d_noop`（空销毁回调），因为 shim 不拥有这些指针的所有权。

### 3、所有权事实（empirically 确认）

以下结论通过 `/_ext/tmp/logs/cairo_probe.c` 逐项验证。每个 case fork 独立进程，一个 abort 不掩盖其它结果。

| API | 所有权 | 验证方式 |
|-----|--------|---------|
| `cairo_get_source()` | **借用**（不增 ref） | fork 后调 `get_source` 再 `destroy`，不 abort |
| `cairo_get_target()` | **借用** | 同上 |
| `cairo_pop_group()` | **调用方拥有 ref**（必须 `destroy`） | 不调 `destroy` 则 valgrind 报 leaked |
| `cairo_set_matrix(cr, NULL)` | — | SIGSEGV（直接解引用 NULL） |
| `cairo_format_stride_for_width(CAIRO_FORMAT_RGB24, 100)` | — | 返回 **400**，非 300（RGB24 也是 4 字节/像素） |
| `cairo_get_dash(cr, dashes, *offset)` | — | 此版本只有 2 个出参（dashes + offset） |
| `cairo_get_font_size()` | — | **此版本不存在**（1.16.0 无此 API） |

这些结论直接决定了 Bug 5 的修法（改用 `d_noop`），也影响了冒烟脚本对 `font_size` getter 的断言设计。

### 3、集成阶段抓出的 4 个问题

#### 3.1 跨模块 metatable 名碰撞（最隐蔽的一个）

`lgishim_pango.c` 和 `lgishim_cairo.c` 各自的 `CLS_NAMES` 都写了 `"lgishim.Context"`，指向**两个不同的 C 类型**（PangoContext* 与 cairo_t*）。

`luaL_newmetatable(name)` 的行为是：名字已注册就**直接返回已有的表**，不新建。`lgishim.lua` 的加载顺序是 pango → pangocairo → cairo，所以 cairo 的 `class_setup` 调 `luaL_newmetatable("lgishim.Context")` 时拿到的正是 pango 那张 metatable，然后把自己的 `__index`/`__newindex`/`__gc`/`finish` **覆盖上去**，还把 cairo 的 Context 方法表装在同一张表上。

后果：一个 pango_context_t 走到 `:set_resolution()`，命中的是 cairo 的 `m_index`，按 cairo 的 `C_CTX=1` 走完全错误的分支——实测结果就是 `panctx.set_resolution == nil`。

**两个维度都得切**：

1. pango 的 `CLS_NAMES` 全部加前缀 `lgishim_pango.`
2. `#define REG_CLASSES` 从 `"lgishim_classes"` 改成 `"lgishim_pango_classes"`

第 2 条不能省——`m_index` 是 `REG_CLASSES[w->cls]` 按**模块内序号**取类信息，而 pango 的 `C_CONTEXT=6` 和 cairo 的 `C_REGION=6` 数值撞车。只改名不切数组，方法表照样取错。

验证探针确认修好：`panctx.set_resolution` 返回 function；反过来 `img.set_text == nil`（cairo.Surface 不会被误当成 pango Layout 拿到 `set_text`）。

#### 3.2 `check_layout` 的栈索引错误

首次实现的 metatable 校验把 metatable 拿在 `-2`，但那一格是 userdata 本身，不是 metatable：

```
luaL_getmetatable(...)  → [.., mt1]
lua_pushvalue(idx)      → [.., mt1, ud]
lua_getmetatable(-1)    → [.., mt1, ud, udmt]     ← -1=udmt, -2=ud, -3=mt1
```

`lua_rawequal(L, -1, -2)` 比的是 udmt 和 ud，永远不等，于是恒返 NULL，`show_layout`/`update_layout` 全线报 `expected a Pango.Layout`。改成 `-3` 即好。

#### 3.3 REGION_PG 属性遮蔽方法

`m_index` 的顺序是 **getter 表优先于方法表**，而且属性 getter 会被**调用**后返回结果。所以 `num_rectangles` 放属性表里，`region.num_rectangles` 读到的是那个整数，`region:num_rectangles()` 就变成"调一个整数"：`attempt to call a number value`。

`wibox/drawable.lua:114` 用的是方法形式，`is_empty` 同理（drawable.lua:112）。两个都从 `REGION_PG` 挪走，只留在 `REGION_M`。

#### 3.4 Pattern 返回值形状 + 一次越界的 lib/ 修改

这是反的——本项目的前提就是上游 `lib/` 保持原样，只换 `require`。已 revert 两文件（确认残留 diff 只剩 `require("lgi")` → `require("vendor.lgishim")`）。shim 侧改为 lgi 的 **status 优先**形状：

### 3、真 bug：`PANGO_CHECK_VERSION` 是子任务编出来的假宏

接手后第一次编译直接失败。子任务写的版本判断是：

**Pango 头文件里根本没有 `PANGO_CHECK_VERSION`** 这个宏——`grep -r "define PANGO_CHECK_VERSION" /usr/include/pango-1.0/` 返回 0。这是 GTK/GLib 家族的命名习惯被无意识套到了 Pango 上，典型的「凭命名惯例推断 API」。

```c
#if PANGO_VERSION_MAJOR * 100 + PANGO_VERSION_MINOR >= 150
    pango_layout_get_preferred_size(chk(L, 1), &ink, &logical);
#else
    pango_layout_get_extents(chk(L, 1), &ink, &logical);
#endif
```

容器 Pango **1.48.10**，所以走 `#else` 分支；1.50 分支留作迁移，不生效。**教训：子任务产出的 C 代码里每一个宏名都要对头文件核实，不能只信名字像。**

### 4、§24 冒烟的三次断言纠错（最有价值的一段）

`10-spike4-cairo-smoke.sh` 新增 §24（+139 行，39 项断言）。一次写了 **3 条「必须抛错」的断言，3 条全错**，逐条实测才改对：

| 原断言 | 实际结果 | 原因 |
|--------|---------|------|
| `set_wrap(Pango.Wrap.WORD)` | `Pango.Wrap` 为 nil | shim 的 pango 模块只导出 `SCALE` / `units_from_double` / `parse_markup`，**枚举表一律不导出**（`WrAP` 表只在 `enum_from`/`enum_to` 内部用）。改传字符串 `"WORD"` |
| `get_extents(0)` 必须抛错 | **不抛** | 第二参数被 `chk(L,1)` 直接忽略，`0` 根本没被读 |
| `get_extents("x")` 必须抛错 | **不抛** | 同上，第二参数不存在 |
| `set_wrap(3)` 必须抛错 | **不抛** | `enum_from` 走 `luaL_optstring`，非字符串被强制转字符串，匹配不到就**静默回落默认值** |

最终定稿的断言（都是实测行为）：

- `set_width("wide")` **抛错** —— `luaL_checkinteger` 拒绝字符串，单位必须是整数
- cairo `Surface` 作为 `Layout` 接收者 **抛错** —— `chk()` 的类型边界

- `get_extents()` 的 ink/logical 与 `get_pixel_extents()` 相差 ≤ 1 `SCALE`（1024）

## 七、并行下发可行性分析（Part 5 / 6 / 8 / 9）

### 0、问题

Part 5 GLib、Part 6 Gio、Part 8 GdkPixbuf、Part 9 GObject 能否四个子任务同时下发？

### 1、结论速览

**不能四个同时下发。** 两个原因，都不是「效率低」，是「会坏」：

| 原因 | 性质 |

| Part 6 依赖 Part 5 | 真依赖 |

### 5、可并行的边界规范

要让多个子任务同时干活又不互相踩，必须**把「写新文件」和「接线」拆开**：

```
子任务 A → lib/vendor/lgishim_glib.c     （只允许碰这一个新文件）
子任务 B → lib/vendor/lgishim_pixbuf.c   （只允许碰这一个新文件）
子任务 C → lib/vendor/lgishim_gobject.c  （只允许碰这一个新文件）
主任务   → lgishim.lua / CMakeLists.txt / 冒烟 §25-27 / 统一构建 / 统一提交
```

三个新 `.c` 文件路径互不重叠，子任务之间**零文件冲突**。主任务集中处理 4 个共享文件，一次构建一次冒烟，串行且快。

配套纪律：

1. **子任务禁止 `docker exec ... ninja`** —— 构建统一由主任务做，避免 §3 的目录冲突。子任务可以用 `09-spike4-cairo-probe-compile.sh` 做单文件语法自检（只产一个 `.o`，不碰构建目录）。
2. **子任务禁止改 `lgishim.lua` / `CMakeLists.txt` / 冒烟脚本** —— 这三处由主任务在接线时一次改完。
3. **子任务禁止改上游 `lib/`** —— 与既有约定一致。
4. **子任务回报必须包含**：新文件路径 + 行数 + 导出的 `luaopen_*` 名字 + `CMakeLists.txt` 需要 append 的行 + `lgishim.lua` 需要加的表项 + 建议的冒烟断言清单。主任务照单接线。
5. **子任务省略 `model_tier`**，继承主任务模型（见 §6）。

### 6、429 的处置

上轮 4 个子任务里 3 个以 `429 insufficient balance` 中断，**全部是显式设了 `model_tier: "medium"` 的**；改用继承模型重试的同一个任务（GLib/Gio scope v2）完整跑完并返回了摘要。用户判断 429 是「调错了模型」，证据链支持这个结论 —— 显式指定 tier 的子任务 100% 失败，继承模型的 100% 成功。

1. **`task` 调用一律省略 `model_tier`**，不要为了省钱或提速显式指定任何 tier。
2. **子任务中断 ≠ 产物丢失**。文件可能已经完整落盘，丢的只是最终回报。中断后第一步是 `git status` / `ls` 确认磁盘状态，再决定重投还是接手。实测案例：scope 盘点子任务中断，但 444 行文档已完整写盘（后来因 API 面漏项弃用，不是因为写盘失败）。

### 6、通用教训：C 里做不出同一性

`lua_setfield(L, -2, "Pixbuf")` 会把栈上的类表**弹出**，此刻栈顶只剩模块表；接着 `lua_pushvalue(L, -1)` 推的是**模块表自身**，`lua_setfield(L,-2,"pixbuf")` 就得到 `module.pixbuf == module`（自引用，不是类表）。而 `lua_pushvalue` 推别的值只能得到**拷贝**，永远不是同一个引用。

结论：**所有需要「同一个表」的别名都必须上收到 Lua 层用赋值实现**（`M.GdkPixbuf.pixbuf = M.GdkPixbuf.Pixbuf`）。C 侧只负责造类表并挂到模块表的一个正名字段上。这条已体现在 `lgishim_pixbuf.c` 的 luaopen 注释里（把 `GdkPixbuf` / `gdkpixbuf` / `pixbuf` 三个别名全删了）。

### 2、luaopen 的栈契约（本篇最贵的一条教训）

`make_class_table()` **把造好的类表留在 Lua 栈上**就返回了。所以 `luaopen_*` 里**每一个类都必须跟一个**：

```c
make_class_table(L, C_FILE);
lua_setfield(L, -2, "File");
```

漏掉任何一行，`package.preload` 照样注册成功、`require` 照样成功、模块表照样非空（其它函数都在），只是那个类的字段是 `nil`。症状是运行期「`Gio.File.new_for_path is nil`」这种最不好定位的一类错。本篇的 `luaopen_lgishim_gio` 补了 **14 个** `lua_setfield`。

### 5、为什么 Gio 空表能活过两篇

篇七 §7 已经知道 `M.Gio = {}`，篇八结尾又写了一次。但它一直没被发现，因为 `lib/vendor/lgishim.lua` 的写法是：

```lua
local ok7, Gio = pcall(require, "lgishim_gio")
...
Gio = ok7 and Gio or {},
```

而 `luaa.c` 只 preload 了 pango / pangocairo / cairo 三个。**gio 从来没有任何 preload 条目**，`require` 永远失败，`ok7` 永远是 false，于是 `M.Gio` 永远是空表——而且这个回退路径「设计正确」，没有任何警告。更要命的是冒烟 harness 自己写了完整的 preload 列表，所以 harness 是绿的，只有真机是坏的。**harness 和真机的 preload 清单是两份独立的事实源，这才是根因。**

补了两道护栏：

1. 冒烟脚本开头（shell 侧）：遍历 `luaa.c` 里所有 `luaopen_lgishim_*`，逐个断言 `luaa.c` 有对应的 `lua_setfield(... "lgishim_xxx")` preload 条目、且 `lib/vendor/lgishim.lua` 有对应的 `require, "lgishim_xxx"`。
2. Lua 侧：`Cairo` / `Pango` / `PangoCairo` / `GdkPixbuf` / `GLib` / `GObject` / `Gio` 七个模块表逐个 `next() ~= nil`——空表立刻炸。

### 6、容器侧的四个坑（已进 memory）

1. **`/tmp` 在容器里是本地盘，不是共享盘。** 只有 `/_ext` 共享。日志写 `/tmp` 然后宿主 `cat`，报的是 `No such file or directory`。
2. **长 `docker exec sh -c '...'` 会静默空跑**：没输出、没文件、退出码 0。短命令和 `sh /path/script.sh` 稳定。一律写成脚本再 exec。
3. **`pkg_check_modules(X_REQUIRED ...)` 的读回变量是 `X_REQUIRED_INCLUDE_DIRS`**。混着写静默拿到空 include 路径，症状是随机找不到头文件。
4. **`G_BUS_TYPE_SESSION` 在这个 glib 里是 `2` 不是 `3`**。写死枚举值之前必须编译 probe 验证一遍，不要凭文档记忆。

另外还有：`lua_pushstring(L, NULL)` 在 Lua 5.3 下断言（`get_name` / `get_display_name` 在属性没被请求时返回 NULL，必须先判空）；`Gio.Async.start(wrapped)(body)` 里 `wrapped` 必须**自己调用**入参，它的返回值被丢弃，所以「返回一个 thunk」的写法什么都不会发生。

**3.1 `AWESOME_STATIC_DEPS=ON` 不是静态开关（最贵的一条）**


不传就编出 `ELF 64-bit LSB pie executable, dynamically linked, interpreter /lib/ld-musl`

**3.2 `CMakeLists.txt:143-147` 变量名 bug（干净构建才暴露）**

`pkg_check_modules(LGISHIM_PANGO_REQUIRED pango pangocairo)` 的 prefix 是 `LGISHIM_PANGO_REQUIRED`，
所以变量名是 `LGISHIM_PANGO_REQUIRED_INCLUDE_DIRS`；代码读的却是 `LGISHIM_PANGO_INCLUDE_DIRS`
（PIXBUF 同理）。干净 build dir 里该变量根本不存在 →
```
lib/vendor/lgishim_cairo.c:42:10: fatal error: pango/pangocairo.h: No such file or directory
```
只有带着 commit `ababafb9`（当时 prefix 还是 `LGISHIM_PANGO`）**残留 CMakeCache 的旧 build dir**
才会因为 stale 缓存"看起来能编"。这正是必须从干净目录出包才能发现的那类问题。
诊断信号：`grep -c 'LGISHIM_PANGO_INCLUDE_DIRS:' <build>/CMakeCache.txt` == 0 即中招。
（GIOUNIX 的 prefix 本身就是 `LGISHIM_GIOUNIX`，不带 `_REQUIRED`，那行本来就对。）

```
GLib-GObject-CRITICAL **: g_object_get_qdata: assertion 'G_IS_OBJECT (object)' failed
```
速率约 **11 MB/s，8 秒 89 MB**。而且**残留的 awesome 进程会一直往同一个日志文件刷**，
实测 4 个残留进程把容器刷到 OOM（docker exit 137）。
`G_DEBUG=disabled` **压不住**（静态链接的 glib 不认这个环境变量）。
目前脚本里靠 `pkill -9` 清理 + 事后删日志兜着，**根因未修**。

**3.9 容器是 busybox 工具链**

- `timeout` **不支持 `-k`**（报 `unrecognized option: k`），只有 `timeout [-s SIG] SECS PROG`
- **awesome 忽略 SIGTERM**，必须 SIGKILL，冒烟判定 rc ∈ {0,124,137,143} 才算"活着"
- `pgrep -c` 不支持；`stat -c %s`、`numfmt --to=iec`、`sleep 0.2` 都支持
- **`pkill -9 -f 'Xvfb :99'` 会杀掉自己**：`sh -c` 的命令行里含这个 pattern，自己匹配自己 → 容器 137

**3.10 脚本自身的逻辑 bug（都是分步跑才暴露的）**

- `UPX_STATE="跳过"` 初始值让 `[ -z "$UPX_STATE" ]` 恒假 → UPX 整段被静默跳过
- `say` 只写 stdout，长构建被 kill 时进度全丢 → 现在同时写日志
- TS 每步重算导致包名漂移 → 现在落在 `$BUILD_DIR/RELEASE_TS`
- `--ultra-rep` 会卡死流水线 → 加了 `UPX_ROUND_TIMEOUT` 单轮兜底

### 4、注意事项

**4.1 出包脚本里塞了太多环境适配 —— 这版是欠账**

`busybox timeout -s KILL`、`pkill -9 -f` 清残留、OOM 兜底、UPX 7 轮重试与超时控制，
这些全是**环境 provisioning** 的事，不该长在出包脚本里。标准的做法是拆两层：

- **环境准备层**：装 upx / Xvfb、装静态依赖、确定工具链（glibc vs busybox）
- **标准出包层**：只假设一个干净的、依赖已就位的环境，干配置→编译→压缩→安装→打包

这版把两层揉在一起了，换环境（比如换成 glibc + 正式 upx 的构建镜像）就要回来改脚本。

**4.2 lgishim_gobject 的 CRITICAL 刷屏未修**

32 项断言全过、`traceback=0`，所以不影响静态化目标的判定，但生产环境里这是真问题。

**4.3 UPX 参数是硬编码的阶梯**

`-1 -3 -5 -7 -9 -9 --lzma --best --lzma --ultra-rep` 写死在脚本里。
换目标架构（arm64 等）UPX 的档位不一定齐，要适配。

**4.4 包名里的版本号是写死的 `4.3`**

`VERSION=${VERSION:-4.3}`。cmake 从 git describe 取到的是 `v4.3-1833-g4c31690c`，
脚本只取了主版本号。要精确版本得自己传 `VERSION=`。

**4.5 冒烟只证明"能启动"，不证明"能用"**

T1 `--version` + T2 Xvfb 下默认 rc.lua 稳定挂 8s 直到 SIGKILL，
**证明的是编译期路径常量生效、不需要 run.sh / LUA_PATH**。
窗口管理、键盘绑定、naughty 通知（无 dbus 会静默降级）都没验证。
Part 13 的 spec 回归才是功能层面的验证。

**4.6 容器环境不是可复现的前提**

这包是在一台跑了很多轮构建的 Alpine 容器里出的。
干净镜像上重跑会踩到不同的坑（比如 apk 版本、静态库缺失），目前**没有**
一份可复现的出包环境定义（Dockerfile / 镜像 tag）。

**4.7 出包脚本对失败的处理偏保守**

任何一步失败就 `fail` 退出并带日志尾部，不会自动重试。
`UPX=0` 可跳过压缩，`SMOKE=0` 可跳过冒烟。

### 4、跑的是真 lgi，不是 shim —— 这一篇到底验证了什么

**全文最容易误读的地方，单独拎出来。**

本次 `LGI_SHIM_FLAG=false`，busted 加载的是系统 lgi 0.9.2（`/usr/share/lua/5.3/lgi.lua`）。
`.busted` 里确实配了 `lpath = "lib/?.lua;lib/?/init.lua;spec/?.lua"`，
但 busted 自身把系统 lua 路径放进搜索链，`spec/preload.lua` 的 `require "lgi"` 先解析到系统那份。

所以这一篇验证的是：

- ✅ **awesome 的 Lua 层（lib/ 下的迁移结果）在真实后端下行为没变**
- ❌ **没有验证 lgishim 本身**——shim 的验证在冒烟侧（829 项断言 / 0 failures）

两半合起来才覆盖「迁移没改坏语义」。

要让 spec 也跑在 shim 上，得掐死 lgi 的解析顺序（`LUA_PATH` 前置 + 让 `spec/preload.lua`
改走 `vendor.lgishim`）。**没做**，而且这有一定代价：`surface_spec` 那 10 个用例在 shim 下
表现未知——shim 里没有 `pixbuf_get_from_surface`，可能变成另外 10 个 error，
也可能整段 `describe` 提前炸，反而看不清 Lua 层的问题。

### 5、`spec/gears/filesystem_tests/y/` 的怪权限是测试自伤，不是仓库问题

第一次 `git status` 报 `warning: LF will be replaced by CRLF in ...`，
`stat -c %a` 是 `702`（`d-wx-wx-wx`，owner 连 read 位都没有）。一开始怀疑是仓库脏了，查了才翻案：

`filesystem_spec.lua` **自己会改夹具权限**：

```lua
os.execute("chmod g-r,o-r,a-r " .. root .. "filesystem_tests/y")  -- :41
assert.is_false(gfs.dir_readable(root .. "filesystem_tests/y"))      -- :44
os.execute("chmod g+r,o+r,a+r " .. root .. "filesystem_tests/y")    -- :47  ← 恢复
```

以 root 跑时，**第一个断言就先挂了**（root 读什么都是可读的，`:26` / `:44`），
代码走不到恢复权限那行，于是把 `y/` 留成 `702`、把 `x/NoRead` 留成 `666`（原 `644`）。

处置：`git checkout -- spec/gears/filesystem_tests/x/NoRead` 恢复 mode，
`chmod 755 spec/gears/filesystem_tests/y/`。**工作区恢复干净**：无 diff、无 stash、与 origin 同步。

教训：这个 spec 的失败**带副作用**。它在断言层挂，但把夹具权限改了。
root 下反复跑这套 spec 会持续污染工作区——这跟 §4.5「冒烟只证明能启动」是同一类问题：
**测试本身对环境的假设没写清楚。**

### 6、Rsvg 空表守卫：唯一一条会真炸的路径

`imagebox.lua:51-58` 的「安全加载」是错的。

`lib/vendor/lgishim.lua:35` 是 `Rsvg = {},`——一个空表占位
（Part 11 已按 Spike 3 D.4 决策 B 砍掉，SVG 渲染没实现）。
而旧守卫只判真值：

```lua
local success, err = pcall(function() Rsvg = lgi.Rsvg end)
```

`pcall` 成功 → `Rsvg = {}`。**空表在 Lua 里是真值** →
`_load_rsvg_handle` 的 `if not Rsvg then return end`（`:75`）**不 return** →
走到 `Rsvg.Handle.new_from_file(...)`（`:87` / `:89`）→ `Rsvg.Handle` 是 nil → 炸。

修法不是再加一层 nil 判断，而是把守卫的语义从「有没有值」换成「有没有我们实际要用的 API」：

```lua
local success, err = pcall(function()
    local mod = lgi.Rsvg
    if type(mod) == "table" and mod.Handle then
        Rsvg = mod
    end
end)
```

（`type` 在文件头已经 upvalue 过，`:36`。）

探针（纯 Lua，把 shim 那份 `{}` 喂进去）：

| 守卫 | `Rsvg` 取值 | 走到 `Rsvg.Handle` 时 |
| --- | --- | --- |
| 旧 | `{}`（真值） | `attempt to index a nil value (field 'Handle')` |
| 新 | `nil` | 直接 `return nil`，优雅降级 |
| 新 + 真模块 | `{Handle={}}` | 正常接受，不误伤 |

`loadfile` 语法检查通过。

**这修的是「降级」，不是「能力」**：SVG 依然渲染不了。
这条守卫的作用是让 imagebox 在不支持 SVG 的后端上**静默走 pixbuf 路径**，
而不是在 `imagebox.image = "icon.svg"` 时抛异常。
这也是为什么 Part 11 砍掉之后这里一直是隐患——**砍掉的功能不会自己消失，守卫会替它兜底**。
