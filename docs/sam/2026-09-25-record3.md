### 1、✅ 已关：刷屏的根因不在 gobject，在 pango 的借用

> 收 record2 篇十二 §7 遗留第 4 项。

篇十一 §3.8 一直把这当成 `lgishim_gobject` 的问题，方向是错的。

`lgishim_pango.c` 的 `pc_font_map_get_default()` 把返回值包进了 `d_unref`（`g_object_unref`）。
而 `pango_cairo_font_map_get_default()` 在 pango 文档里是
`(transfer none) — owned by Pango and must not be freed`；容器里的 `PangoFontMap`
又是真 GObject。于是 Lua 临时值被回收的那一刻，单例的最后一个引用就被减掉了，
pango 的 per-thread `g_private` 从此握着悬垂指针。

**独立复现**（Xvfb `:97`，20000 次走 `textbox.lua:513` 那一整句原文）：

| 包装器 | 结果 |
| --- | --- |
| `d_unref`（修前） | `Pango-CRITICAL pango_font_map_get_serial: assertion 'PANGO_IS_FONT_MAP (fontmap)' failed` → **signal 11** |
| `d_noop`（修后） | 20000/20000 pass ok，0 critical，stderr 716 bytes |

改动就一行。冒烟 830 checks / 0 failures（基线 829/0，+1），二进制 9,597,256 bytes 不变。

**值得记的偏差：** 我一开始用纯 C 探针没复现出来——只跑到 `PANGO_IS_FONT_MAP` 断言，
**没有**跑出 `g_object_get_qdata`。后者是在更完整的路径（默认 rc.lua 全流程）上才出现的，
属于同一个 use-after-free 的不同表现。

**别再把它当 gobject 问题去改 `lgishim_gobject.c`。**

#### 2.1、包名里的四段号是怎么来的（2026-09-25 补）

样例 `awm-static-musl-4.3-1910-5247a66-260925-204338.tar.gz`：

| 段 | 示例值 | 来源 |
| --- | --- | --- |
| 产品名 | `awm-static-musl` | 脚本里硬编码的 `PKG`，可用 `PKG=` 覆盖 |
| 版本号 | `4.3-1910` | `git describe --tags --long` → 去 `v` 前缀、去 `-g<sha>` 尾巴 |
| 提交号 | `5247a66` | `git rev-parse --short=7 HEAD` |
| 时间戳 | `260925-204338` | `TZ=UTC-8 date +%y%m%d-%H%M%S`；首次生成后写进 `$BUILD_DIR/RELEASE_TS`，分步跑时不再变 |

**`1910` 不是我们的迭代次数，是「离上游 tag 有多远」。**

`git describe --tags --long` 原始输出是 `v4.3-1910-g5247a666`，其中 `1910` = 从 tag
`v4.3`（`5da5d361`，Merge PR #2619）到打包 HEAD 的**提交总数**——
`git rev-list --count v4.3..5247a66` 实跑就是这个数。它把上游 master 在 v4.3 之后
累积的历史也全算进去了（`git shortlog -sne v4.3..HEAD` 里绝大部分是上游提交，
我们自己的约 150 条），所以**它是累计里程，不是本地改动量**。

**这就是为什么它单调往后变：** HEAD 每前进一步，哪怕只是 docs commit，下一次出包这个
数就会 +1。刚推完真实环境反馈章（现 record4 一）打钩的 `16be0e51` 之后，`git describe --tags` 已经变成
`v4.3-1911-g16be0e51`；现在重跑流水线包名会是 `4.3-1911-16be0e5`，但二进制与上一包
逐字节相同，因为 docs 不进编译产物。

> **判断两个包是否等价要看第三段 `SHA`，别看第二段 `VERSION`。** 第二段只是里程表。

两处可调：

- `VERSION=4.3-1910 bash docs/sam/scripts/11-package-static-release.sh 7` —— 固定版本号，
  只跑打包步骤时避免包名漂移
- 打上新的 tag（如 `v4.4`）后 `git describe` 自动改认最近的 tag，尾号从 0 重新数起

### 3、✅ 已关：Part 12 的 T2 冒烟是假通过

修完 pango 之后跑一遍全流水线，T2 **失败**：rc=1。

对照 09-24 的 `step6.out`：

| | 修前（`4c31690`） | 修后（`59b4cf7`） |
| --- | --- | --- |
| T2 rc | 137 | **1** |
| 判定 | `T2 ok 默认 rc.lua 启动并稳定挂满 8s` | `FATAL: T2 失败` |
| traceback | 0 | 2 个 |
| 冒烟日志 | **89,502,335 bytes** | 4,243 bytes |

**修前的 89.5MB / 8s ≈ 11.2 MB/s 就是那次刷屏**，而 rc=137 只是「8 秒还没死」。
真相是旧二进制卡在 pango 的 use-after-free 里，**rc.lua 根本没加载完**——
`traceback=0` 不是干净的证据。

修完之后 rc.lua 真的执行了，于是炸出两个**一直被掩盖**的缺陷：

1. `rc.lua:97` → `imagebox.lua:112: attempt to index a userdata value (local 'surf')`
2. `rc.lua:122` → `textclock.lua:160` → `gears/timer.lua:102: lgishim.GLib.timeout_add: interval must be > 0`

**第 2 个值得单独说：`wibox.widget.textclock()` 不带参数就会炸。** `textclock.lua` 里
`_private.refresh = refresh or 60` 有默认值，但第 160 行把裸 `refresh`（nil）直接传给了 timer：

```lua
w._private.refresh = refresh or 60          -- 有默认值
w._timer = timer.weak_start_new(refresh, cb) -- 传的是裸 refresh = nil
```

`timer.new({timeout=nil})` → `data.timeout = 0` → `timeout_add(..., 0, fn)`。
真 glib 接受 interval 0（立即触发，回调里再改成 `calc_timeout(60)`），所以上游从来没事；
shim 在 `lgishim_glib.c` 里把 `interval == 0` 当错误抛了。

**这是 shim 语义跟 glib 不一致，不是 lua 代码错。** 修法见 4.2——
改 `textclock.lua`（上游 bug），不是放宽 shim。

冒烟脚本已经补了 **T2b**：光看退出码不算通过，日志里出现
`traceback|attempt to call|bad argument|interval must be|E: awesome` 就直接 `fail` 并打印匹配行。
这一条以后不会再漏。

### 4、✅ 已关：两个真缺陷的修法（2026-09-25）

一条改动是 C（`lgishim_cairo.c`），一条是 Lua（`textclock.lua`）。都是根因修，不是绕过。

#### 4.1、✅ 已关：imagebox 的 `surf`：cairo.Surface() 把 lightuserdatum 原样透传了

报错点 `imagebox.lua:112` 的 `surf.width`。顺着 traceback 往回找：

```
capi.awesome.pixbuf_to_surface()   luaa.c:330  lua_pushlightuserdata(L, surface)
       ↓
gears/surface.lua:67  cairo.Surface:is_type_of(_surface)   -> false
       ↓
gears/surface.lua:72  cairo.Surface(_surface, true)        -> surface_wrap()
```

两个关键事实：

* `is_type_of` 比的是**元表身份**（`m_is_type_of` 里 `lua_getmetatable` + `lua_rawequal`）。
  lightuserdatum 没有元表，所以永远是 false——`surface.lua:67` 那个提前返回
  对 pixbuf 加载出来的图**永远不会命中**。
* 于是所有 pixbuf 图都落到 `:72`，而 `lgishim_cairo.c` 的 `surface_wrap` 原来只有一句
  `if (lua_isuserdata(L, 1)) { lua_pushvalue(L, 1); return 1; }`。
  `lua_isuserdata` 对 light/full 都返回 true，所以 raw 指针被原样塞回 Lua，
  `surf.width` 就炸在「attempt to index a userdata value」上。

修法是给 `surface_wrap` 补 lightuserdatum 分支，包成真正的 Surface userdata：

```c
if (lua_islightuserdata(L, 1)) {
    cairo_surface_t *s = lua_touserdata(L, 1);
    if (!s)
        return luaL_error(L, "lgishim: cairo.Surface(): NULL surface");
    return push_obj(L, s, d_surface, C_SURFACE);   /* d_surface = cairo_surface_destroy */
}
```

所有权对得上：`draw_surface_from_pixbuf()` 走的是 `cairo_image_surface_create()`，
返回**带 ref 的新 surface**，`luaa.c:329` 也明写「lua has to make sure to free the ref
or we have a leak」。原来 lightuserdatum 一路没人收，是**真在漏**；现在包成 userdata
由 `__gc` 收，顺带把泄漏也堵了。full userdata 走原来的 `pushvalue` 分支，不会二次包装。

**通用教训：** shim 里凡是「把外部指针接进 Lua 栈」的转换函数，都要区分
lightuserdatum（要包装、要接管所有权）和 full userdata（原样透传、不接管）。
`lua_isuserdata` 不区分，必须用 `lua_islightuserdata`。

#### 4.2、✅ 已关：textclock 的 interval 0：上游 bug，改 Lua 不改 shim

```lua
w._private.refresh = refresh or 60          -- 默认值在这里算好了
w._timer = timer.weak_start_new(refresh, cb) -- 却把裸 refresh 传进去
```

`refresh` 为 nil 时 `data.timeout = 0`，而 shim 在 `lgishim_glib.c` 把 `interval == 0`
当错误。真 glib 接受 0（立即触发），所以上游一直没暴露。

**决策：改 `textclock.lua:160` 传 `w._private.refresh`，不动 shim。** 理由有三：

* 这是**上游就存在的 bug**（默认值算了没用），不是 shim 误报；`w._private.refresh`
  这个字段存在的意义就是承载解析后的值。
* `gears.timer` 文档本就要求 timeout > 0，shim 拒绝 0 更严格，不算语义漂移。
* 改一行比放宽 shim 的检查面小、也更不容易掩盖别处的 0 间隔。

grep 过 `timeout = 0`：只剩 `lib/naughty/` 的通知超时属性（不是 `gears.timer`），干净。

#### 4.3、✅ 已关：gio 回调错误接 traceback，顺带查了那条 transient 错误

上面两个修掉之后，冒烟日志里出现过一条
`lgishim_gio callback error: attempt to call a string value`（D-Bus 连不上之后紧跟一条）。
它被 shim 的 `pcall` 吞掉、只打了一句话，**没有 traceback**——光看消息根本没法定位。

顺手把 `lgishim_gio.c` 的两处回调 `pcall` 接上了 `debug.traceback` 作为 msghandler
（新增 `push_traceback_h()`）：

> 必须在回调**还在栈上**的时候抓。pcall 一旦返回，栈已经展开，事后调
> `debug.traceback` 只会拿到空栈，只能当 msghandler 用。
>
> 另外注意 `lua_pcall(L, nargs, nres, hidx)` 的 `hidx` 语义：函数位置是
> `hidx - nargs - 1`，不是在栈顶下数。所以在 args 之后 push handler 是安全的。

接上之后这条错误就没再出现：**连续 10 次冒烟全绿**（rc=137 / 838B / 错误行 0）。

**它不是被压掉的**——pcall 带 msghandler 不可能吞错，任何 raise 仍会打印。
排除过两个嫌疑：

* 不是脏显示环境。刻意造过「先留一个 WM 占着 `:99` 再起一个」的脏环境，
  只有 `acquire_WM_Sn` 报错、没有这条 gio 错误。
* 不是陈旧目标文件。`ninja -n` 说 up to date，十个 shim 的 `.o` 没有一条比源文件旧。

结论是**无法在干净环境下复现**。既然已经接上 traceback，下次真出现就能直接看到是哪个
`lib/` 帧抛的，不用再猜。

#### 4.4、✅ 已关：环境坑：容器把源文件改成 root:root 444

出包脚本 step 5 之后 `lib/vendor/lgishim_gio.c` 变成了 **root:root 444**（容器里以 root 跑），
宿主机直接 edit 会报 `Permission denied`。`chown headless:headless` + `chmod 664` 恢复即可。
`find . -path ./.git -prune -o -user root -print` 确认全仓库只有这一个文件被改坏。

**值得在出包脚本收尾加一条 chown。**

另外两个容器里跑命令的坑：

* **ninja 必须带 `AWESOME_IGNORE_LGI=1`**，否则 lgi-check 步骤失败。注意失败的 ninja
  可能已经编完/链完目标才报错（并行），二进制 mtime 是新的属正常现象。
* **`docker exec` + 后台进程会卡住输出管道**：`Xvfb ... &` 继承了 stdout/stderr，
  管道不关，docker exec 挂到超时、外层拿到空输出。解法：`docker exec -d` 起 +
  输出写容器内文件 + 另开一次 exec `cat`。Xvfb / awesome 都要显式
  `</dev/null >/dev/null 2>&1`。

### 2、✅ 已关：🔴 step 4 现在是陷阱：会静默装回旧二进制（PRISTINE 三态状态机）

实测（`/_ext/tmp/awe-build-release/`）：

```
awesome           9,597,256  02:49  md5 e4bb95fd…   <- 当前，未压缩，含最新修复
awesome.pristine  9,597,256  00:04  md5 5a7a5463…   <- 旧轮次（4c31690），同大小不同内容
upx.done          pristine=9597256 args=-9 --lzma size=3402220   <- 陈旧
awesome.upx-round1..5                                <- 旧轮次残留
```

`step_upx()` 的短路条件是「**pristine 缺失** + upx.done 存在 → 跳过」。
现在 pristine **存在但陈旧**，逻辑反过来了：直接跑 step 4 会拿旧 pristine 当输入跑 7 轮阶梯，
再 `cp -a` 写回 `$BINARY`，然后 step 5 装、step 7 打包，**全程无任何报错**。

**必须先删 `awesome.pristine` + `upx.done` + `awesome.upx-round*` 才能跑 step 4。**
另外 `RELEASE_TS` 只写一次，新包会和旧包共用时间戳并排存在，极易拿错，建议一起清。

##### 4.1.4、第 15 项：root 误判定位到了，是环境问题不是 shim bug

- **root 属主文件：0 个**。`find lib spec -type f -not -user $(id -un)` = 0，工作区已干净。
- 那「2 个误判」就是 `filesystem_spec.lua:26`（`file_readable`）与 `:44`（`dir_readable`），
  都报 `Passed in: (boolean) true / Expected: false`。
- **根因（复核时纠了一次误判）**：`:23` 是 `os.execute("chmod g-r,o-r,a-r ...")`，
  `a` = owner+group+other，644 减掉全部 read 位 = **600**。
  第一版分析说是「跑 spec 的用户就是夹具属主，600 仍有 rw」——**这是错的**：
  宿主机 `id -un` 是 `headless`，但 busted 在 `builder-awe` 容器里跑，
  容器里是 **root（uid=0）**，夹具属主是 uid=1000。真实机制是 **root 绕过 DAC**，
  600 之后 root 照样可读。两种说法都导致断言必败，但机制不同。
  测试假设「跑测者既非属主也非 root」，本环境不满足，**与 shim 无关**，
  可以从 shim 缺口清单里划掉。
- **副作用属实，且比审计说的更糟**：恢复 chmod 写在 `it()` 体内（`:29` / `:47`），不在
  `teardown` / `after_each`，断言一失败就跳过。而且**恢复是非对称的**——`a-r` 把 644 降到
  600，`a+r` 再加回去落成 **666 而不是 644**。实测 `spec/gears/filesystem_tests/x/NoRead`
  当前就是 `rw-rw-rw-`。git 只跟踪可执行位，所以这个漂移 git 看不出来。

**已实施**（`spec/gears/filesystem_spec.lua`，+49/−6，夹具文件零改动）：
1. 4 条恢复 chmod 收进 `after_each`，`it()` 体内只留「设置严格模式」；
2. 恢复改显式 `chmod 644`（文件）/ `chmod 755`（目录），不再用对称的 `a+r`；
3. 两个不可测断言加条件 skip。busted 2.0.0-0 **没有 `skip()`**（`type(skip)==nil`），
   用 `pending(reason)`，输出 `ok N - # SKIP <reason>`；仓库已有先例 `color_spec.lua:255`。

**跨身份矩阵（本轮最值钱的产出）**——用 `setpriv --reuid` 实测三分支，证明这三条断言
**结构性不可测**：

| 跑测者 | 结果 |
| --- | --- |
| root（本容器默认） | skip，原因「root ignores mode bits」 |
| uid 1000（夹具属主） | skip，原因「owner keeps rw after chmod a-r」 |
| uid 12345（非属主非 root） | **`Operation not permitted`**——无权收紧他人文件 |

所以「配好 non-root 用户就能跑」不成立：非属主无权收紧权限，属主/root 又始终可读。
skip 是最终正确形态，不是临时绕开。顺带证明 `after_each` 在断言抛错后确实执行
（uid 12345 全失败场景下权限仍被还原）。

**实测结果**：该 spec `1..15 → passed 13 | skip 2 | failure 0`；跑完后 `NoRead` 回到
`644`、`filesystem_tests/y` 回到 `755`（跑前是 666 / 333）。

两个非显然坑已进 memory：busted 2.0.0-0 无 `skip()`；Lua 5.3 `os.execute` 失败时
首个返回值是 `nil` 而非 `false`。

depth，但第 4 个参数是 `bits_per_sample`**。depth 由 `bits_per_sample * n_channels` 推出，
`TRUE` + `24` 得到 bits_per_sample = 6，触发
`GdkPixbuf-CRITICAL: gdk_pixbuf_calculate_rowstride: assertion 'bits_per_sample == 8' failed`，

happy path 由 RAISED 转为 `ok type=userdata`，6 条错误路径全部抛清晰文案、无 segfault，

补 `get_pixels` 约 6 行，是下一个 API，不在这轮三项范围内。

#### 2.3、get_rgba 签名不匹配（2.1 #2）详解 ✅ 已关

真实 lgi `cairo.Pattern:get_rgba()` 返回 **5 值 `(status, r, g, b, alpha)`**，
首值 `"SUCCESS"` 或错误串，永不抛 Lua 错。调用方按这个契约写：

```lua
-- color.lua:305  create_opaque_pattern
local _, _, _, _, alpha = pattern:get_rgba()
-- color.lua:368  change_opacity
local error, r, g, b, _ = input:get_rgba()
if error ~= "SUCCESS" then return input end
-- color.lua:401  to_rgba_string
local error1, error2, r, g, b, a = pcall(function() return col:get_rgba() end)
if (not error1) or error2 ~= "SUCCESS" then return color.to_rgba_string(fallback) end
```

shim 的 `pattern_get_rgba` 却：

```c
// lgishim_cairo.c:1228-1240
if (cairo_pattern_get_rgba(p, &r, &g, &b, &a) != CAIRO_STATUS_SUCCESS)
    return luaL_error(L, "lgishim: pattern is not a solid color");  // 抛 Lua 错
lua_pushnumber(L, r); ... lua_pushnumber(L, a);
return 4;                                                            // 只 4 值
```

于是三处 caller 全静默坏掉（不崩、不报错，结果就是错的）：

- `create_opaque_pattern`：`alpha = 第5值 = nil`，`if alpha ~= 1 then return` →
  **恒返回 nil**，opaque-pattern 优化路径永远走不到。
- `change_opacity`：`error = r（数字）`，`error ~= "SUCCESS"` 恒真 →
  **恒返回 `input`**，改透明度是空操作。
- `to_rgba_string`：`pcall` 成功、`error2 = r`，`error2 ~= "SUCCESS"` 恒真 →
  **恒回落 fallback**，颜色转 hex 全走默认。

修法与之前 `get_color_stop_rgba` 一致（`lgishim_cairo.c:1359-1361` 注释已锁
「lgi puts the cairo status first」契约）：返回 5 值、首值 `"SUCCESS"` 或错误串、
不抛 Lua 错。

✅ 修法已在 `ab674820` 落地（见 2.1 #2 关闭状态列）。

### 3、推翻一个假设：`Screen.primary` 不是 4 widget 失败根因 ✅ 已关

sub-agent 报告 4 个 widget `.draw` 失败根因是「Xvfb 无 primary → Screen.primary

P0-2 的修法（"强制 screen.primary 非 nil"）方向不对；正解是 **让冒烟塞一个假
tray client**，或让 `systray.lua:118` 在 `tray.clients` 空时仍走一次 draw 路径。

✅ **已关**：T2c probe 里 `forced_entries = 2` 已 override `awesome.systray()`

「假绿」担忧是 2P0 修复前的状态（那时 `matrix_shim_used=true`、`utd_calls=0`）。
