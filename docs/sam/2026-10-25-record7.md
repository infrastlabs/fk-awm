#### 1.1.2、复核新发现的缺口（原文没覆盖）

##### 1. 漏了第三个崩溃点：`CloseNotification`（`lib/naughty/dbus.lua:359`）

```lua
function notif_methods.CloseNotification(_, _, _, _, parameters, invocation)
    local obj = naughty.get_by_id(parameters.value[1])   -- 360 行，(uu) tuple
```

死法与 1.7 表里两处完全一样：tuple 类型串以 `(` 开头 → `g_variant_type_element` 断言
→ SIGABRT。触发条件是**任何外部 app 调 `Notifications.Close`**（关单条通知、通知中心
「全部关闭」）。所以真实的崩溃点是 **3 个**，原文的「两个崩溃点」表述不准确。

好消息是三个都在同一个函数里，方案 A 一处改动同时堵住——但排查时的清单要补上这个，
否则修完第二个它会立刻冒出来。

##### 2. 方案 A 修完，带图通知**仍然不显示**（影响最大的一条）

`lib/naughty/dbus.lua:209-265` 的 image-data 分支在真正 `naughty.notify(args)`
（304 行之后）之前执行：

```lua
if hints.icon_data or hints.image_data or hints["image-data"] then
    for k, v in parameters:get_child_value(7 - 1):pairs() do   -- 214 行
```

`parameters` 是 DBusVariant userdata，没有 `get_child_value` → **Lua 错误抛出 →
handler 中断 → 整条通知被丢弃**。flameshot「复制到剪贴板」正是带 `image-data` 的通知。

所以单走方案 A：**WM 不崩了，但这条通知依旧不出现**，只是从「拖垮整个 WM」降级成
「静默丢通知 + 一条日志」。原文 1.10 结尾那句「要保住『awesome 自己显示通知』就必须
走 A」需要修正——A 只是必要条件，不是充分条件。

> 顺带一句：原文 1.10 方案 C 拿 `dbus.lua:214` 当「Lua 侧绕不过去」的证据，方向对，
> 但没指出这行本身在真机构建里就是一个**活 bug**（不只是绕过手段不存在）。

##### 3. 测试把这个缺口掩盖了

`tests/examples/shims/dbus.lua:20` 用 `setmetatable({value={...}},
{__index=parameters_miss})` **假造**了 `get_child_value`：

```lua
local function parameters_miss(t, k)
    if k == "get_child_value" then
        return function(idx) return t[idx-1] end
    end
end
```

所以带图的测试用例全绿，真实构建里却是死代码。这是典型的 **shim API 缺口被测试层盖住**，
和之前 `gears.surface get_pixels` 那类缺口同源。

##### 4. 就算补上 `get_child_value`，`ay` 语义也不对

shim 的 ARRAY 分支（`lgishim_gio.c:780-802`）对非 dict 元素数组是**逐元素递归**，
`ay` 会变成「整数表」`{1,2,3,...}`；而 upstream/LGI 对 `ay` 的 `.value` 是字节串，
字节要走 `Variant.data`。`dbus.lua:211` 那句注释「`.value` breaks with the array of
bytes (ay)」当年就是为了让步于这个才改走 `get_child_value` 的。

所以要完整支持 image-data，得同时补三样：`DBusVariant.get_child_value`、
`Variant.data`、`ay` 的字节串语义。

##### 5. 小项：maybe 类型（`m...`）在 switch 里没有 case

会落 `default` 被 `g_variant_print` 打成字符串——不崩，但语义错。D-Bus 的 `a{sv}`
里几乎不会出现 maybe，记为潜在项，不在本次修复范围。

##### 6. 附录第一条已核实，第二条核不到

`lib/awful/screen.lua:365-366` 确实是
`return capi.awesome.startup and c.screen or screen.focused()`，`startup` 为真时会对
nil `c` 解引用。但原文引用的 `~/.config/awesome/module/notifications.lua:155` 在部署侧、
不在本仓，本次无法核对，保持原文标注。

**缺口四：`is_variant_userdata` 的判定被循环覆写（`lgishim_gio.c`）**

`names[] = { "lgishim.GLib.Variant", "DBusVariant" }`，循环里写的是
`ok = lua_rawequal(L, -1, -2)` 而不是 `ok = ok || lua_rawequal(...)`。
`GLib.Variant()` 对象由 `lgishim_glib.c` 造出、元表名恰好是第一项，
第一轮命中后第二轮必然不匹配，`ok` 被覆写成 0。后果：`dbus.lua:360`
的 `invocation:return_value(GLib.Variant('(u)', { id }))` 被判成「不是 variant」
→ `luaL_error 'expected a Variant at arg 2, got userdata'` → 受保护调用兜住 →
**没有任何 D-Bus 方法调用收到回复**，Notify 全部超时。也就是说崩溃修掉之后，
通知能创建显示（探针收到 DISPLAY），但调用方拿不到 id —— 这一步不修，A 白修。

**缺口五：`variantwrap_pairs` 把 `lua_next` 当迭代器用（本记录唯一一处段错误）**

`variant_wrap_push` 造的容器是真 Lua 表，所以 C 里写的是
`lua_pushcfunction(L, (lua_CFunction)lua_next)`。这是错的：`lua_next` 是 C API
形式，第二个参数是**表在栈上的下标**；而 Lua 调用 for 循环迭代器时传的是
`f(L, nargs)`，两参数调用下 `nargs = 2`，于是它解引用的不是表而是**控制键**
（第一轮是 nil，之后是上一轮返回的字符串），`idx2addr` 落到栈顶之外。
那一格内存装的是什么取决于布局：nil 就抛 `"invalid key to 'next'"`，
别的值就是一次裸 SIGSEGV。**其余五种形状全过，只有带 image-data 的走
`parameters:get_child_value(6):pairs()`，一迭代就崩。**

定位线索：给 rc 挂 `debug.sethook` 后同一处从 SIGSEGV 变成 Lua 错误
（栈布局变了、越界读到的是另一种垃圾）—— 这是栈越界的典型指纹。
再用一个只跑 `next`/`pairs` 的最小用例验证「普通表 + 带 `__index` 的元表」
迭代完全正常，排除元表本身，锁定迭代器拿错参数。
库函数 `next()` 是 Lua 自带的另一个包装，它自己从 `func + 1` 读表、不走
`idx2addr`，所以正解是 `lua_getglobal(L, "next")`。

同一个提交里还清掉了本次新增代码的 GVariant 引用泄漏：`variant_wrap_push`
现在有明确所有权约定（接收的那一个引用归它自己，要么自释要么在 a{sv}
解包时移交），字典分支去掉多余 `g_variant_ref`、元组子项与 `ay` 字节项
各自 unref；`variant_bytes_push` 每字节 unref —— 原先一张 100 字节的图
泄漏 100 个 GVariant。`variant_to_lua` 的 VARIANT/ARRAY/TUPLE 三分支
同样是 ref 多一配 unref 少一，一并配平。

### 1.3、`✅` 触发通知 → 显示通知全链路 + 与 dbus / dunst 的关系（2026-10-25）

代码行号对应当前 HEAD（`9c44aec99` 前一批提交，`b3cc77d32` 及之前的源码）。

#### 1.3.1、全景：谁在监听、谁在应答

一句话心智模型：**dbus-daemon 是路由器，不是目的地。**
`org.freedesktop.Notifications` 是 session bus 上的一个**名字**，持有这个名字的
那个连接收到 Notify 方法调用。awesome 只是候选持有者之一，dunst /
xfce4-notifyd / notify-desktop / xcb-notify 都是。

所以「通知走到哪条链路」既不取决于发送方（它连名字以外的东西都不知道，1.3.2），
也不取决于 awesome 内部（它在被叫到之前完全没参与，1.3.3），**取决于谁先持有
那个名字**（1.3.4）。结论一句话：**链路分叉点只有一个，在 dbus-daemon 上那个
名字的持有者，不在任何客户端里。**

下面按这个顺序讲：1.3.2 触发端 → 1.3.3 awesome 侧接收并显示 → 1.3.4 分叉点在哪
→ 1.3.5 「崩」与「静默」两种失效形态。

#### 1.3.2、触发端（发送方）：只知道名字，不知道谁来显示

Flameshot / notify-send / 任何程序只做两步：① 找 session bus 地址
（`DBUS_SESSION_BUS_ADDRESS`，或 `$XDG_RUNTIME_DIR/bus` 自动找）；② 向
`org.freedesktop.Notifications` 发 `Notify (susssasa{sv}i)`。

它不关心谁接，也不检查谁接了 —— 只是等一个 `(u)` 回来。所以发送方视角的
「成功」**只能证明「总线上有人答了」，不能证明是 awesome**（谁持有见 1.3.4，
怎么判见 1.3.5）。这也是为什么通知链路的验证必须两条腿走路。

发送方自己也会在这一步失败：没有 `DBUS_SESSION_BUS_ADDRESS` 也没有
`$XDG_RUNTIME_DIR/bus` 时它连不上总线，那是它自己的错，跟 awesome 无关 ——
排查时先分清是哪一头。

#### 1.3.3、awesome 侧（接收 → 显示）

#### 1.3.4、如何走到不同的链路：分叉点在哪

分叉发生在 **dbus-daemon 查名字持有者**那一刻：

```
dbus-daemon ── 查 org.freedesktop.Notifications 谁持有 ──┬── awesome            → 走 1.3.3 那条链路
                                                          ├── dunst              → awesome 完全不知情
                                                          ├── notifyd / desktop  → 同上
                                                          ├── 无持有者 + .service 文件
                                                          │       → bus 自动拉起 dunst，再补发一遍
                                                          └── 都无 → NameHasNoOwner
```

| 持有者 | 发生的事 |
|---|---|
| awesome | 走 1.3.3 完整链路，naughty 弹出 |
| dunst | awesome 完全不知情；通知进 dunst 的堆栈 |
| xfce4-notifyd / notify-desktop | 同上 |
| 无持有者但有 `.service` | bus 自动拉起 dunst，再补发一遍 Notify |
| 都无 | `NameHasNoOwner` |

第四行就是「共享总线上连发 5 条得出 OK id=2..5」假阳性的来源：
`/usr/share/dbus-1/services/org.freedesktop.Notifications.service` 的
**服务自动激活**把 dunst 拉起来答的，不是 awesome。共享总线得出的
「某些形状不崩」是串扰，不可信 —— 这也是 matrix.sh 改成真实环境版后
**必须先跑 `owner` 子命令**确认持有者的原因（`GetNameOwner` 出 unique name，
`GetConnectionUnixProcessID` 换成 unix pid，和 pgrep 到的 awesome pid 比对）。

**决定谁是持有者的三件事**：① 谁先调 `own_name`（1.3.3 那段代码）；
② 桌面自启有没有配 dunst（`~/.config/autostart/*.desktop`）；③ 那个 flag
（`NONE` vs `ALLOW_REPLACEMENT`）。所以「为什么通知进 dunst 不进 awesome」的
答案**不在这两个程序里，在会话启动顺序里**。

**两个独立维度，别混淆。**

*session bus ≠ system bus。* 通知全走 session bus。静态构建日志里那条
`a_dbus_connect:618: Could not connect to D-Bus system bus` 跟通知无关 ——
是 `dbus.c:652` 那条 system 连接失败，容器里没装 system dbus 时的正常现象。

*dbus-1 (C) ≠ GLib/Gio (Lua)。* 同一个 daemon，两套客户端库，两条独立连接：

| | 库 | 连接 | 能力 |
|---|---|---|---|
| `dbus.c` | libdbus | `dbus_connection_session` / `dbus_connection_system`（`dbus.c:650-653`） | 只有 `request_name` / `release_name` / `add_match` / `remove_match` / `connect_signal` / `disconnect_signal` / `emit_signal`（`dbus.c:857-869`） |
| `lib/vendor/lgishim_gio.c` | GLib GDBus | `Gio.bus_own_name` 那条 | 完整 `own_name` / `register_object` / `call_sync` / `emit_signal` |

关键：**C 侧（dbus-1）没有入站方法调用的分发能力**，所以通知服务器只能是
Gio 那条。这也解释了为什么这条链路的崩溃点全落在 C/Lua 交界的 shim 层 ——
只有那条路会真的接 method call。

#### 1.3.5、修复前为什么「崩」和「静默」是两回事

| | 形态 | 触发点 | 怎么看 |
|---|---|---|---|
| 崩 | SIGABRT / SIGSEGV，进程挂 | C 层 GLib 断言、`lua_next` 误用 | pid 存活 + `SIG:` 行 |
| 静默 | 进程活着、通知不出现、日志只留一条 `Error during a protected call` | Lua 层抛错被 `pcall_dispatch` / `protected_call` 兜住 | `send` 那行拿没拿到 id + 日志新增行 |

前者修 `g_variant_type_element`（1.1.3 步 A）/ `variantwrap_pairs`（1.1.3 步 C）；
后者修 `get_child_value` / `.data`（1.1.3 步 C）/ `is_variant_userdata`（1.1.4）。
所以修完必须两路都验：**pid 活着只能证明没崩，拿得到 id 才能证明通知真的进了
链路** —— `notify_triggers.py` 打印的 `OK id=N` 是判后者的唯一凭据。

顺带两个同类静默：

- `bus_connection` 在信号侧（`sendActionInvoked` :61 / `sendNotificationClosed`
  :75）判 nil 后静默不发。名字被抢走后，发送方会以为通知还开着。
- `replaces_id` 指向的通知不属于发送方时（`_private._unique_sender` 校验，
  :313），只打一条 warning 然后照常新建 —— hijack 请求不会炸，也不会被拒。
