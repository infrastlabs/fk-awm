### 1、D-Bus（B 项）解析：`dbus_bus_get` 与编译期默认路径（2026-09-28，只解析未改）

**现象**：设了 `DBUS_SYSTEM_BUS_ADDRESS` 后 `./awesome -r` 仍报：

```
a_dbus_connect:618: Could not connect to D-Bus system bus: Failed to connect to
socket /usr/local/var/run/dbus/system_bus_socket: No such file or directory
```

**结论链（代码级）**：

1. **awesome 4.3 用 libdbus，不是 GIO GDBus**：`dbus.c` a_dbus_connect（618 行）直接
   `dbus_bus_get(type, &err)` → system bus 地址由 **libdbus** 解析。
2. **libdbus 的规则**：先读 `DBUS_SYSTEM_BUS_ADDRESS` 环境变量；没设就用**编译期默认**。
3. **编译期默认 = 静态 libdbus 的 `${localstatedir}/run/dbus/system_bus_socket`**：
   构建时 `--localstatedir=/usr/local/var` → `/usr/local/var/run/dbus/system_bus_socket`
   （record3 五·4 已定案的根因，不是新问题）。
4. **`./awesome -r` 不吃新 export**：`-r` 是给正在跑的实例发重启信号，它 exec 自己、
   继承**自己启动时的环境**。实测 `/proc/<pid>/environ` 里没有
   `DBUS_SYSTEM_BUS_ADDRESS`——shell 里的 export 进不去那个进程。
5. **目标 socket 其实存在**：`dbus-daemon --system --nofork` 在跑，socket 在
   `/run/dbus/system_bus_socket`（`/var/run` 是软链指向 `/run`）——所以全新启动 +
   正确格式的 env 就能连上，警告消失。
6. **env 格式**：裸路径（`/var/run/dbus/system_bus_socket`）libdbus 不认，
   必须是 `unix:path=/var/run/dbus/system_bus_socket`。

**生效方式（部署侧，未执行）**：

```sh
kill <当前 awesome pid>          # -r 不行，必须杀
export DBUS_SYSTEM_BUS_ADDRESS=unix:path=/var/run/dbus/system_bus_socket
/usr/local/static/awm/bin/awesome
```

**根本解法（未排期）**：重编静态 libdbus 加 `--sysdir=/run/dbus`（record3 五·4 方向 2）。
env 只是部署侧临时覆盖；不处理也不崩（naughty 降级 + 1 行无害警告）。

### 2、遗留尾巴清单

## 二、freedesktop 排查：另一台机器仍走 else 分支（2026-09-27 排查 / 2026-09-28 并入收尾）

> 本内容原存 `/_ext/tmp/2026-09-27-freedesktop-else-branch-diagnosis.md`（临时），
> 用户指令并入本文件二级章节。**收尾状态：根因确证为「包内缺模块」+「部署侧补三件套」**
> （见下方 4、当前环境验证）。用户确认右键菜单已正常加载 freedesktop 全量桌面菜单。

### 1、背景

- 用户在**另一台机器**上按文档复制 freedesktop 三件套到
  `/usr/local/static/awm/share/awesome/lib/freedesktop/`，启动 static/awm 后右键菜单
  **仍是 else 分支（Debian 静态菜单）**。→ 待用户反馈探针结果。
- 本容器 (`docker-hdmi-desktop-desktop-1`) 实测：**不带 `--search` 直接启动，
  `require("freedesktop")` = true**（编译期默认搜索路径已含
  `/usr/local/static/awm/share/awesome/lib`）。→ 复制位置对了就不需要 `--search`。
- **根因**：静态构建包的 CMake install 规则只拷贝标准目录 (`lib`, `themes`, `icons`)，
  未包含 `freedesktop/`（纯 Lua 模块，不在 upstream 源码树内）。需从 apt 安装版手动复制三文件。

### 2、可能原因（按概率）

1. **`~/.config/awesome/rc.lua` 遮挡 `/etc/xdg/awesome/rc.lua`** —— 用户级 rc 优先加载，
   若没有 has_fdo 分支就一直走自己的 Debian 菜单。
2. **那台机器的包/前缀与容器不是同一版** —— 拷贝路径必须落在该二进制的编译期搜索路径上；
   旧包/不同前缀时拷到 `/usr/local/static/awm/...` 无效。
3. **freedesktop 依赖在那台缺**（require 内部报错）—— `pcall` 捕获后照样 false；
   本容器核实过 `menubar/menu_gen.lua`、`menubar/icon_theme.lua`、`gears/*` 全在。
4. **启动方式：`awesome -r` 是重启正在跑的实例** —— 若另有 apt 版占着 WM selection，
   `-r` 重启的是那个，不是 static/awm。

### 3、定位探针（在那台机器上跑）

```sh
cat > /tmp/pf.lua <<'EOF'
local ok, m = pcall(require, "freedesktop")
print("has_fdo =", ok, "| 错误: ", ok and "无" or tostring(m))
print("package.path 前两段 =", (package.path:gsub(";.*", "")))
EOF
DISPLAY=:0 timeout 6 /usr/local/static/awm/bin/awesome --config /tmp/pf.lua
ls -la /usr/local/static/awm/share/awesome/lib/freedesktop/
strings /usr/local/static/awm/bin/awesome | grep -E "share/awesome/(lib|themes)"
ls -la ~/.config/awesome/
```

判读：
- `module 'freedesktop' not found` → 原因 2（搜索路径没覆盖，贴 strings）
- 其他 Lua 报错 → 原因 3（依赖缺失，贴错误串）
- `has_fdo = true` 但桌面仍 else → 原因 1 或 4（rc 遮挡 / 起错实例）

### 4、✅ 当前环境验证（hdmi-desktop, 2026-09-28）

**部署操作**：
```sh
sudo mkdir -p /usr/local/static/awm/share/awesome/lib/freedesktop
sudo cp /usr/share/awesome/lib/freedesktop/{init.lua,desktop.lua,menu.lua} \
   /usr/local/static/awm/share/awesome/lib/freedesktop/
```

**验证结果**：
- freedesktop 三件套已成功复制至 `/usr/local/static/awm/share/awesome/lib/freedesktop/`
- rc.lua 有 `has_fdo` 分支 (行 23: pcall + 行 100: if)
- 用户确认「**右键菜单与动态版对上了**」→ freedesktop 全量桌面菜单生效
- 问题根因确证为「包内缺模块」+「部署侧补三件套」，非代码缺陷

## 三、主题兼容排查：fk-awesome-wm-theme 静态版跑不起来（2026-09-28）

> 主题仓库：`https://gitee.com/g-system/fk-awesome-wm-theme`（clone 到 `~/.config/awesome` 使用）。
> **现象**：静态编译版跑不起来，apt 版可以。排查出两个问题：`vicious` 缺失（已修，
> 部署侧）+ `read_line_async` shim 缺口（待修）。

### 1、根因一：`vicious` 缺失（✅ 已修，部署侧）

- 主题 5 处 `require("vicious")`（先炸点 `modules/widgets/cpu_widget.lua:3`），
  vicious 是第三方 widget 库。
- **apt 版 awesome 的 lib 自带 `/usr/share/awesome/lib/vicious/`；静态包 lib 是裁剪树，
  没有** → `module 'vicious' not found` → rc.lua 加载失败（**跑不起来的直接原因**）。
- 主题不依赖 lain（README 提到但实际未 require）；主题自带全部 modules/widgets（已核对）。
- **处置（同 freedesktop 模式，部署侧复制，不进仓库）**：
  ```sh
  sudo cp -r /usr/share/awesome/lib/vicious /usr/local/static/awm/share/awesome/lib/vicious
  ```
- 复现验证：vicious 报错消失，rc.lua 继续跑下去（进入根因二）。

### 2、根因二：`DataInputStream.read_line_async` shim 缺口（✅ 已修，2026-09-28）

- 复制 vicious 后暴露：**音量/麦克风 widget**（`modules/widgets/{volume,microphone}_widget.lua`）
  与 vicious 里用 `awful.spawn.with_line_callback` 的 widget（hddtemp 等）读子进程输出失败：
  ```
  lgishim_gio read_line_async error: attempt to call a lgishim_gio.DataInputStream value
  ```
- 隔离探针证实（回调里第一行 `cb obj` 从未打印）：**`lgishim_gio` 的 `read_line_async`
  回调根本没被调用**——`lgishim_gio.c:1343` 的 C 实现内部 `lua_pcall` 的栈布局/errfunc
  处理有缺陷；方法表里 `read_line_async` 已注册（`lgishim_gio.c:1488`）。
- **影响**：WM 正常启动运行，仅这些 widget 的数值/状态显示空白（音量条、麦克风、
  hddtemp 等）。**不阻断主题运行**，但 widget 残废。
- **✅ 已修（2026-09-28，commit `97727f86`）**：根因 = `lua_pcall` 按 `top-nargs` 取函数，
  而 `push_traceback_h` 把 errfunc 推在函数+参数**之上**，函数索引落到 stream 上 →
  「attempt to call a lgishim_gio.DataInputStream value」。修法：**先推 errfunc，
  再推 callback+参数**。实测：回调被调用（`cb obj = DataInputStream`）、首行读出
  （`hello line1`）、`read_line_async error` 归零。
- **出包**：`awm-static-musl-4.3-1832-97727f8`（UPX 3,903,068 B）已部署，
  部署版裸跑终验同通过。
- 顺带发现① `read_line_finish` 的 length 恒 0（`pending_len` 读取前被清零）——
  ✅ **已修（`8632bc73`）**：清零移到 push 之后，实测 `len = 11`（`hello line1`）。
- 顺带发现② `pcall_dispatch`（glib 派发回调路径）——✅ **已修（`8632bc73`）**：
  errfunc 用**绝对索引** `gettop-nargs-1` 插到 callback 之下（此前相对索引在有栈残留
  时会错位 → `attempt to call a string value`；clean/带残留栈都正确）。实测主题跑
  **无 `lgishim_gio callback error`**（record3 那条「transient gio 回调错误」随之消除）。
- 以上两项 + read_line_async 修复合入包 **`awm-static-musl-4.3-1835-8632bc7`**（已部署，
  部署版裸跑终验：`cb obj`/`hello line1`/`len = 11`/`pcall = true`）。
- 主题剩余报错为**环境问题**（非 shim）：`rc.lua:184 secondary_output`（主题按多屏
  假设，Xvfb 单屏）、`volume_widget:79` 空音频服务。

### 3、遗留与顺带

1. **read_line_async shim 缺口**：排期修（lgishim_gio.c 异步回调 + 重编出包）。
2. **`~/.config/awesome` 非 git 仓库**：`git pull` 报 `not a git repository`——主题文件是
   复制放置的（无 `.git`），更新需重新 clone 或手动换文件。
3. **vicious 部署侧复制不进仓库**（同 freedesktop 决策）。

### 4、lib 差异全景：静态版 vs apt 版（2026-09-28，只分析未改）

**顶层**：apt 独有 8 项（`bashets.lua` / `cyclefocus/` / `flaw/` / `freedesktop/` /
`obvious/` / `revelation/` / `tyrannical/` / `vicious/`）——**除 freedesktop 外全是
Ubuntu/Debian 打包捆绑的第三方模块**；静态独有 `ruled/`（上游 4.3 规则模块）+
`vendor/`（lgishim shim）；共同 `awful / beautiful / gears / menubar / naughty / wibox`。

**文件级**：apt **289 文件 / 3.1M** vs 静态 **259 文件 / 2.8M**；226 个共同文件里
**119 个内容不同（diff 共 37,258 行）**——根因是 **`lgi → lgishim` 系统性替换**：
apt 28 个文件 `require("lgi")`，静态改写为 `require("vendor.lgishim*")`（41 处，
波及所有碰 cairo/pango/gdk-pixbuf 的文件）。唯一残留的 `require("lgi")` 在
`vendor/lgishim.lua:52`（有真 lgi 优先用真的——回退逻辑，有意保留）。

**其他**：themes 120 vs 108（静态裁 zenburn titlebar PNG 12 个 + 加
`xresources/wallpaper.svg`）；icons 相同（4）；rc.lua / awesome-client 不同；
二进制本质不同（apt 动态依赖 .so vs 静态 10M 构建 / UPX 3.6M）。

**为什么这么大**：同源（都基于 awesome 4.3）不同流、**用途相反**——apt 捆绑第三方
求「开箱全功能」；静态版按需裁剪求「自包含」（第三方 + freedesktop 全裁掉，缺的
部署侧补）。**运行时不同是最大推手**：静态无 lgi 动态绑定，必须把 lib 里所有 lgi
调用改写为内置 shim——这一项占了 37k diff 的大头。
**推论**：以后跑第三方主题/模块缺文件时，按 vicious/freedesktop 同款「部署侧复制」
补即可，不用进仓库（除非用户拍板）。---

## 四、静态 lgishim 环境新坑：lib 版 wibox 重绘链三坑（2026-10-05 分析）

> 现象源：`fk-awesome-wm-theme/docs/03-awesome-c-lua-architecture.md`
> （2026-10-02/04 实测记录）「静态 lgishim 环境新坑（lib 版实测）」三点。
> 本小节为原因分析与修复思路（先只分析未改，待复现定位后再修）。

### 1、三坑现象、逐个分析、共同根因与修复思路

**共同特征**：三坑都发生在 **widget 状态变化触发「重绘/重排」** 时，capi 裸版
（无 lib 重绘链）全正常：

| 坑 | 触发 | 断点特征 |
| --- | --- | --- |
| 1 textclock | 每秒 timer → set_text | 整条 panel 消失（静态 textbox 正常 → 排除初始绘制） |
| 2 struts | workarea 变化（workarea=1052 生效） | struts C 层正常，panel 消失 |
| 3 竞态 | 启动首次调度 | 偶发 panel 缺失 |

三条链都汇到同一处：

```
widget 状态变化 → widget::redraw → timer.delayed_call（GLib timeout）
   → do_redraw → cairo 绘制
```

（`lib/wibox/drawable.lua:393-403`：重绘用 `timer.delayed_call` **合并调度**，
每次重绘都要过一次 GLib timeout。）

**坑 1（textclock 整条消失）**
- 链路：gears.timer 每秒 → `set_text` → textbox 尺寸变化 → `widget::redraw` →
  `timer.delayed_call` → **`lgishim_glib.c:464` 的 `timeout_cb`** → `do_redraw` → cairo。
- 疑点 A（高）：`timeout_cb` 用**裸 `lua_call` 而非 `lua_pcall`**（`lgishim_glib.c:464`）
  ——重绘链里任何 Lua 错误直接裸传播穿过 C 帧（GLib 源回调内），状态不可控 →
  面板后续全空白。与已修的 gio `pcall_dispatch` **同族缺陷**。
- 疑点 B（中）：`do_redraw` 的 cairo 绘制在 shim 下失败（surface 生命周期 / X
  surface 数据访问，见坑 3 的 B）。
- 疑点 C（低）：set_text 后 pango 排版测量异常 → 布局塌成 0 尺寸。

**坑 2（struts 后消失）**
- 链路：`wibox.struts`（`lib/wibox/init.lua:240-242` 代理到 drawin）→ C 层 struts
  生效（workarea=1052 ✓）→ `awful.screen` workarea 变化信号 → wibar 重排 → 重绘
  （同坑 1 链）。
- 疑点 A（高）：同坑 1——workarea 变化触发的重绘走同一条 `delayed_call` 链。
- 疑点 B（中）：workarea 变化信号的**派发链**（GObject 信号 → `lgishim_gobject`
  closure_marshal）若也属「未保护 pcall」族 → 回调没跑 → 面板几何没更新。
- capi 裸 drawin+struts 正常 → C 层无问题，问题在 **lib 层对 workarea 变化的响应**
  （信号 + 重绘）。

**坑 3（偶发不渲染，竞态）**
- 首次绘制也是异步（`delayed_call`），竞态在「drawin 映射 vs 首次重绘」。
- 疑点 A（高）：`timer.delayed_call` 的 dispatch 在启动早期偶发被吞（lgishim_glib
  timeout source 与主循环的注册/移除时机）→ 该次 run 首绘不执行。
- 疑点 B（中）：X 上 map 与首次 draw 的先后，静态二进制 X roundtrip 时序不同 →
  部分 run 里 draw 落在 map 前被丢弃。

**共同根因（最可能）**

> **wibox 重绘调度链在静态环境不可靠**：`widget::redraw → timer.delayed_call
> （GLib timeout）→ do_redraw → cairo`。其中 **`lgishim_glib.c` 的 `timeout_cb`
> 用裸 `lua_call`（无保护、无错误记录）** 是最大嫌疑——链上任何一处 Lua 错误裸
> 传播、破坏后续 dispatch；这同时解释定时触发（坑1）、workarea 触发（坑2）、
> 启动首绘偶发（坑3）。

**修复思路（分步，先复现定位再动手）**

1. **复现 + 打点**：Xvfb 探针分别跑 textclock / struts / 连续 N 次截图；在
   `delayed_call` 回调、`do_redraw`、drawin draw callback 各步打点，看断在哪一步；
   A/B 对照 apt 动态版。
2. **修 `lgishim_glib.timeout_cb` → `lua_pcall`**（带 traceback + `g_printerr`，
   与已修的 gio `pcall_dispatch` 同族同法）——先暴露真实错误、杜绝裸传播。
3. **查 `lgishim_gobject` 信号派发**（closure_marshal / awful.screen workarea

**✅ 2026-10-05 已修复并验证（三坑共同根因坐实 + 三处修复）**：

## 五、spawn 修复、渲染复核与 lgishim 补缺（2026-10-06）

### 1、`easy_async` 回调不可靠：C stack overflow（✅ 已修 2026-10-06）

> 源：记忆 `lgishim-static-build.md` 2026-10-06 实测（calla 排查）+
> 本日复现/根因/修复。

**现象**：`awful.spawn.easy_async` / `easy_async_with_shell` 回调时好时坏；
`with_line_callback` 逐行回调正常；**多路并发 + 大输出**时
`lgishim_gio read_line_async error: … C stack overflow`，easy_async 用户回调
永不触发；小输出命令正常 → 表现为「不稳定」而非「完全不能用」。
后果：把后续动作包在 easy_async 回调里的代码路径**静默失败**（stderr 无痕，
很多 rc.lua 忽略返回值），calla 的 4 条 autostart（rc.lua:114-133）曾全哑。

**复现**（当前包 4.3-1844）：`seq 1 3000` 并发 2 路 + `sh -c 'echo e1 >&2; echo o1'`
→ 2× C stack overflow，big1/big2 回调不触发，mixed 正常。

**根因**：shim 的 `DataInputStream.read_line_async` **内联同步**调回调
（无 glib 派发，读一行→立即 pcall 回调）→ spawn.lua 的
`start_read → read_line_async → callback → start_read` 按行数递归，N 行输出
= N 层 C/Lua 嵌套 → 大输出 C 栈爆。EOF 判定无问题（spawn.lua 加载时空流
`read_line` 探测 → 现代模式 `not arg`，`(nil, 0)` 正确判 EOF）。

**修复**（`lgishim_gio.c`，commit `758b5aaa`）：读行后 **`g_idle_add` 主循环
调度** `datain_async_dispatch` 派发 `callback(obj, nil)`（下一轮迭代执行），
打断递归；stream/callback 用 `luaL_ref` 保活（stream ref 连带保 datain_ctx），
派发后 unref + `lua_settop(0)` 清栈。

**验证**（部署版裸跑）：压力 `seq 1 3000` ×2 + mixed **三路回调全触发**
（stdout 13893 B）、零 overflow、无「left on the Lua stack」警告；回归
easy_async / with_line_callback 正常。出包 `awm-static-musl-4.3-1826-758b5aa`
已部署。

**教训**：GIO 异步回调在静态 shim 下必须**真异步**（主循环调度），不能内联
同步——否则任何「回调里再发起」的链式用法都会按深度递归；这类缺口症状是
「静默失败 + stderr 无痕」，排查靠判别法（with_line_callback 有输出、
easy_async 回调 print 打不出来）。

**踩坑记录**（本批过程中修的）：

1. **`lgi.pango` 大小写**：shim 暴露的是 `Pango`（大写），旧代码写小写会失败。

   若用 `luaL_checkinteger` 会报 "number has no integer representation"。
6. **`Path.pairs` 返回顺序**：next 函数返回 `(index, segment)`——
   写反 `for i,seg in pairs(path)` 会拿 segment 当 i，seg 当 seg 但被解释错。

## 七、titlebar SVG 图标颜色丢失：根因定案 + 修复方案（2026-10-09）

> 触发：静态版 titlebar 按钮图标全部显示黑色/深棕（用户报告），SVG 输入渲染成
> 黑/灰度、PNG 输入渲染正常。本小节 = 根因定案 + 修复方案 + 实施记录。

### 1、根因定案与修复方案（2026-10-09）

**实测铁证**（静态 awesome + lgishim 探针：`gears.surface.load` 解码 → `write_to_png`
落盘 → PIL 取像素）：

| 输入 | 解码结果 |
|---|---|
| `close.svg`（24×24，fill=#85ACFB + opacity 0.22~0.30） | 中心 `(73,50,40,77)`，主色 `#22140d`/`#4a3225` —— 深棕黑 ❌ |
| `close_focus.png`（16×16，archkiss 原图） | 中心 `(133,172,251,255)` = `#85acfb` 纯蓝，主色 `#85acfb` ×20 ✅ |

**根因**：`lib/vendor/lgishim_pixbuf.c` 的 `surface_to_pixbuf()`（`:818`，仅 SVG 路径
使用；PNG/JPEG 不走它）把 cairo ARGB32 表面按字节**原样 memcpy** 进 GdkPixbuf，
两个错：

1. **通道序错位**：cairo ARGB32 在 little-endian 内存字节序是 `B G R A`，
   GdkPixbuf 约定 `R G B A`——未重排，R↔B 互换。
2. **premultiplied 未反预乘**：`close.svg` 每块是 `fill=#85ACFB` + `opacity≈0.27`，
   librsvg 渲染后 premul ≈ `(36,46,68,69)`；通道错位后 B=68 落到 R 位 →
   R 通道最大（红为主）→ 深棕黑，与实测 `#4a3225`（R 最高）吻合。

PNG 路径 libpng `PNG_FORMAT_RGBA` 直出 straight RGBA、字节序本来就对 → 蓝。
半透明（低 opacity）图标必炸；不透明纯色 SVG 可能不明显。

**修复方案（shim 层，一处函数）**：改 `surface_to_pixbuf()` 像素拷贝循环
（`:1063` 附近），每像素：

```
读 [B,G,R,A]（cairo ARGB32 小端，CAIRO_ARGB32_GET_* 宏解码）
a≠0 时反预乘：r=r*255/a, g=g*255/a, b=b*255/a
写 [R,G,B,A]（straight RGBA）到 GdkPixbuf
```

对齐动态版 gdk-pixbuf/librsvg loader 与 libpng 路径的 straight RGBA 输出语义。
约 15 行改动，重编出包后 SVG 图标颜色恢复，**PNG 替换方案不需要**。验证回归 =
本节探针（SVG 应变为 `#85acfb` 蓝）。

**状态**：🔶 根因已定案，修复实施中（2026-10-09）。探针：容器内 `/tmp/probe_svg.lua`。

### 2、根因修正：静态 librsvg 渲染空转，不是 surface_to_pixbuf（2026-10-09 续查）

> ⚠️ **推翻 1 节结论的核心**：`surface_to_pixbuf` 通道序 + premultiplied 是真实
> 缺陷（保留修复），但**不是**黑屏根因。改完该函数后实测 SVG 输出变成**全透明**
> （99B 空 PNG）——因为 librsvg 渲染出来的本来就是空图，转换函数只是如实搬运。

**证据链（全实测）**

| 测试 | 结果 |
|---|---|
| 静态探针（`gears.surface.load` close.svg → write_to_png → PIL 取像素） | 全透明；PNG 对照 `#85acfb` 纯蓝 |
| **独立静态测试**（脱离 awesome：静态 librsvg 2.40.21 + 静态 cairo 直连，连纯红不透明方块 SVG） | `rsvg_handle_render_cairo` 返回 `ok=1`，surface 全零，`cairo_status=0` 无错误 |

### 3、根因再修正：回到 surface_to_pixbuf（librsvg 全程正常）（2026-10-09 深夜续查）

> ⚠️ **推翻 2 节结论**：2 节的「静态 librsvg 渲染空转」是**误判**，源于三处
> 调试错误（见下）。真根因就是 1 节的 `surface_to_pixbuf`，且修复落地时又踩了
> 两个自己的代码缺陷。librsvg / libcroco / cairo 从头到尾**全部正常**。

**误判链（我的调试错误，逐一还原）**

1. **像素坐标盲区**：所有「透明」证据（rt2/rt3/rt4 的 p0/p11/p40、rsvg_dbg 的
   tmp0、pixbuf_dbg 的 pix0）读的全是**画布角落/矩形外**像素——close.svg 的
   小方块在 viewBox(5,5)~(10,10)（24px 下 ≈7.5~15px），角落本来就是 0。
2. **插桩位置**：GD trace 插在 `em=width` 赋值**之前**，打印出 em=0 的假象；
   混合归档（ar `u` 警告）又放大了混乱。
3. **循环代码缺陷**：修复循环先漏列偏移（每列都写第 0 列互相覆盖 → 全透明），
   加偏移时又放在 x 循环外（x 是上一行残留 w → 越界写 → 段错误）。

**决定性证据（全像素扫描，坐标无关）**

| 版本 | close.svg 解码结果 |
|---|---|
| 旧二进制（memcpy） | 深棕 `#4a3225` 系（通道序错位 + premultiplied） |
| 修复后（列偏移错误） | 全透明（每列写第 0 列互相覆盖） |
| **修复后（列偏移在 x 循环内）** | **蓝色 `#80a8ff`/`#83a8fc` 系 ×76 像素，alpha 17-76 对应 0.22~0.30** ✅ |
| PNG 对照 close_focus.png | `#85acfb` a=255 ×20 ✅ |

**独立静态测试**（脱离 awesome，同一静态 librsvg）：不透明红矩形
中心 = `ffff0000` 纯红；opacity 0.5 = `80800000` 半透明红——**静态 librsvg
渲染完全正常**。

**最终根因（与 1 节一致，修复落地）**

- `lib/vendor/lgishim_pixbuf.c` `surface_to_pixbuf()`：cairo ARGB32

- 修复：逐像素 `CAIRO_ARGB32` 位移解码 → 反预乘 → 写 straight RGBA；
  **列偏移 `+ x*4` 必须在 x 循环内**（踩过两次坑）。

**状态**：✅ **已修复定案**。验证回归 = 容器内 `/tmp/probe_svg.lua`（全像素

## 九、内存占用：官方默认配置实测与减量梳理（2026-10-13）

### 1、默认配置实测 + 系统性减量分析

> 触发：用户 top 观察主题配置 RSS ≈ 86M，问官方默认配置多少、如何减。

**实测**（部署静态 awesome 不带 `-c` → 编译期默认 rc
`/usr/local/static/awm/etc/xdg/awesome/rc.lua`；Xvfb 1280x800；HOME=/root）：

| 时刻 | RSS | VSZ | 说明 |
|---|---|---|---|
| 5s（启动中） | 17,160 KB (~17M) | 25,648 KB | 加载/渲染中 |
| 30s（稳定后） | **33,552 KB (~33.5M)** | 42,028 KB | 默认 rc 全部 widget 起完 |

`/proc` 稳定态明细：`VmData`（堆）21,292 KB、`VmExe` 6,512 KB、
`RssAnon` 31,456 KB、`RssFile` 2,096 KB、无子进程。

**对照**：官方默认 ≈ 33.5M；用户主题 86M（top）——差量 ~52M **全部来自配置侧**
（modules/widgets、bling、vicious、freedesktop、每屏 wibox 全量加载），非二进制
差异。

**内存去向分解（静态版特有）**

| 去向 | 量级 | 说明 |
|---|---|---|
| 二进制本体 | ~6.5M（VmExe） | **全静态链接**：librsvg/cairo/pango/glib/gdk-pixbuf/lua/X 全编进单进程，无法跨进程共享（动态版走共享库多进程复用）——静态设计固有成本，基本不可改 |
| Lua 堆（VmData） | ~21M | 模块加载缓存 + widget 对象树 + GC 未回收对象 |
| wibox 客户侧 surface | 数 M | 每个 widget 的 cairo image surface（客户进程内） |
| 图标/字体缓存 | 数 M | beautiful 图标 surface、字体 cache |

**减量策略（按性价比排序）**

1. **Lua GC 参数**（零成本、见效最快）：默认 rc 未调 GC。设
   `collectgarbage("setpause", 100)` / `"setstepmul", 200)`；**启动完成后
   `collectgarbage("collect")` 一次**把启动期峰值（theme/icons/widgets 全量构造）
   压回——预期稳定 RSS 砍 10-30%。
2. **surface/图像缓存上限**：`gears.surface` 按路径缓存图像；确认/设置缓存上限，
   图标缓存可按需。
3. **naughty 清理**：通知超时自动销毁 + 定期 `naughty.destroy`，避免残留累积。
4. **配置侧瘦身**（针对 86M 主题）：widget 按需 require（CPU/GPU/蓝牙不用不
   加载）；bling 只 require 用到的模块；vicious 只注册用到的；freedesktop 菜单
   一次性构建后释放中间表。
5. **静态构建侧**（改动大收益小，不优先）：`-Wl,--gc-sections` 剔未用符号
   （strip 已做，收益有限）；librsvg 等已必然驻留。
6. **X 侧**：wibox 的 X pixmap 占 X server 内存（不计 awesome RSS，但受限环境
   总内存要考虑）——减少多余 background surface、避免高分辨率重复贴图。

**建议顺序**：1（GC 收紧 + 启动后 collect）→ 3（通知清理）→ 4（配置按需加载），
预期主题稳定 RSS 86M → 60-70M；静态二进制本体 6.5M 不变。

落地 GC 方案。
