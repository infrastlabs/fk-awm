### 3、✅ 已解决：A：XPM 报错 → gdk-pixbuf 找不到 loader（有日志，缺陷确凿）

> **✅ 已解决（2026-09-26，commit `71e3aa7b`，见 12.8.11）**：`lgishim_pixbuf.c` 的
> `pixbuf_new_from_file` 改成 magic-byte 分发 + 自解码——PNG 走 libpng 简化 API、
> JPEG 走 libjpeg、XPM 走自写解析器，未知格式回退 `gdk_pixbuf_new_from_file`。
> 宿主 Xvfb 验证：`background.png`(2048x1536) / `awesome.xpm` / `xterm_32x32.xpm` /
> `filled-xterm_32x32.xpm` / `video-001.jpeg` 全部加载成功，缺文件与未知扩展名优雅返回 nil。
> 一·10 判定的「三层失败」结论本身不变，但结论指向的出路（shim 自解码）已经落地。
> 顺带修掉解析器里一个真 bug：`sscanf("%x")` 直接写 `unsigned char*` 会把相邻 width 冲成 0。

**取证**：pristine 二进制 rodata，offset `5789859` 起连续四段：

```
GDK_PIXBUF_MODULE_FILE   /usr/local/lib   gdk-pixbuf-2.0   2.10.0
```

`loaders.cache` 在 `5787112`，紧挨着 `gdk_pixbuf_init_modules` 和错误串
`Couldn't recognize the image file format for file %s`。

→ 运行时拼接出的 loader cache 路径是 **`/usr/local/lib/gdk-pixbuf-2.0/2.10.0/loaders.cache`**
（静态 libgdk_pixbuf 用 `--prefix=/usr/local` 构建，`libdir=/usr/local/lib`）。
用户机器上真正的 loader 在 `/usr/lib/x86_64-linux-gnu/gdk-pixbuf-2.0/2.10.0/loaders/`。
`strings | grep -c "usr/local/lib/gdk-pixbuf-2.0"` = **0** → 确认是运行时拼接，不是单一字面量，
所以符号表里看不到完整路径，只能靠相邻段拼。

**机制**：`gdk_pixbuf_init_modules()` 只认那个 cache 文件，不扫目录。找不到 cache →
**零 loader** → 每次 `gdk_pixbuf_new_from_file()` 都报"无法识别格式"。这正是 shim
`pixbuf_new_from_file()`（`lib/vendor/lgishim_pixbuf.c:319`）原样透传的 `error->message`。

**关键推论**：这条报错能出现，说明 `/usr/share/pixmaps/awesome.xpm` **在用户机器上是存在的**
（apt 残留）——文件不存在会报 `Failed to open file`，不会报"无法识别格式"。

### 4、⬜ 仍未修：B：D-Bus 连不上 → 构建前缀烤死（有日志，缺陷确凿）

> **⬜ 仍未修（2026-09-26 复核）**：这条**不是** awesome 的 prefix 问题，所以本轮把
> awesome 的 prefix 改到 `/usr/local/static/awm` **不会**改善它。烤死的是**静态 libdbus 自己**的
> `localstatedir = /usr/local/var`，纠正它要在**构建 libdbus 那一步**加
> `--sysdir=/run/dbus` 重编 libdbus（一·9 方向 2），不是重编 awesome。
> 影响面维持原判：仅 `naughty` 通知降级 + 一行警告，不崩。
> 临时绕过仍可用 env：二进制里命中 `DBUS_SYSTEM_BUS_ADDRESS` 字面量，可被覆盖。

**取证**：二进制里同时存在两条：

```
unix:path=/usr/local/var/run/dbus/system_bus_socket   ← 静态 libdbus 烤死的，正在用的这条
unix:path=/var/run/dbus/system_bus_socket              ← 另一处（gio）
```

libdbus 用 `localstatedir = ${prefix}/var` = `/usr/local/var` 构建，system bus 路径整个错位。
**对照**：容器**系统** libdbus 烤的是 `/run/dbus/system_bus_socket`（正确）——说明是构建前缀问题，
不是 libdbus 本身的问题。同一二进制里 `/usr/local/bin/dbus-launch`、`/usr/local/share/lua/5.3/...`、
`/usr/local/share/:/usr/share/` 全是 `/usr/local` 前缀，同一批烤死。

**可覆盖**：二进制里命中 `DBUS_SYSTEM_BUS_ADDRESS` / `DBUS_SESSION_BUS_ADDRESS` 字面量 → 支持 env 覆盖。

**影响**：仅 `naughty` 通知降级 + 一行警告，不崩。

### 6、✅ 定案：D：菜单无图标 → 我们包缺 `lib/freedesktop/`，不是解码，也不是主题

**✅ 定案（2026-09-27，代码级 + 双二进制 A/B 实证）**

**根因是内容缺失，不是缺陷**——我们的包没打包 `lib/freedesktop/`，而 apt 版 rc.lua 的
主菜单是靠这个模块生成的。缺它 = 静默降级到 Debian 静态菜单 = 只有 2 条硬编码 XPM 图标。

**1. apt 版 rc.lua 的双分支**（`/etc/xdg/awesome/rc.lua`，apt 4.3-5build1 原样）：

```lua
-- rc.lua:23
local has_fdo, freedesktop = pcall(require, "freedesktop")

-- rc.lua:100-112
if has_fdo then
    mymainmenu = freedesktop.menu.build({   -- 全量桌面菜单：解析 .desktop + 分类树
        before = { menu_awesome }, after  = { menu_terminal } })
else
    mymainmenu = awful.menu({ items = { menu_awesome,
                    { "Debian", debian.menu.Debian_menu.Debian },   -- 静态降级菜单
                    menu_terminal, } })
end
```

**2. 我们的包里没有这个模块**：`share/awesome/lib/freedesktop/` 不存在；仓库 `lib/` 顶层只有
`awful beautiful gears menubar naughty ruled vendor wibox`；`git log --all -- lib/freedesktop`
为空 → **这个 fork 从头到尾没收录过它**（apt 版有 3 个纯 Lua 文件：init/desktop/menu）。
于是 `require("freedesktop")` 失败 → `has_fdo = false` → 永远走 else 分支。

**3. else 分支的菜单就是「只有 Pstree 有图标」的出处**：`/etc/xdg/awesome/debian/menu.lua`
是 menu 系统**静态生成**的（文件头写着 `Do not edit`），多级级联约 20 条里**只有 2 条**
带图标路径：

```lua
{"awesome", function() awesome.exec("/usr/bin/awesome") end, "/usr/share/pixmaps/awesome.xpm"},
{"Pstree", "x-terminal-emulator -e ".."/usr/bin/pstree.x11", "/usr/share/pixmaps/pstree16.xpm"},
```

用户看到的「多级级联菜单里只有 Pstree 一项有图标」= 这份静态菜单的**设计产物**。
「图标像老主题」= `/usr/share/pixmaps/*.xpm` 就是 X11 时代的遗留 XPM，本来就长那样。
**与解码、shim、二进制、GTK 主题全部无关。**

**4. A/B 实证**（同一探针 `--config` + Xvfb，逐行对比两个二进制）：

| 项 | apt `/usr/bin/awesome` | 静态 `/usr/local/static/awm/bin/awesome` |
| --- | --- | --- |
| BINDING | `lgi`(apt 动态) | `vendor.lgishim`(静态) |
| `require("freedesktop")` | **true** | **false** |
| `.desktop` 数 | 52 | 52 |
| 带 `Icon=` 字段的 | 52（全有） | 52（全有） |
| `lookup_icon` 命中 | **46 / 48** | **46 / 48**（命中的名字逐个相同） |
| 未命中 | `image-viewer` `preferences-desktop-theme` `multimedia-volume-control` `user-desktop` `system-file-manager` `xfsm-logout` | 同 6 个 |
| 10 个常见名直连（`org.gnome.Terminal` 等） | 全 nil | 全 nil |

### 10、gdk-pixbuf 插件机制能否完全静态化（2026-09-25，三层失败）

用户问题：gdk-pixbuf 要 dlopen `.so` loader，跨 musl / glibc 发行版会失败吧？有办法完全静态化吗？

**结论**：会失败，而且是**三层**，第二层结构性的。上次给的一·9 方向 1 是错的，已撤回。

#### 10.1、第 1 层：loader cache 路径烤死（一·3 已坐实）

`/usr/local/lib/gdk-pixbuf-2.0/2.10.0/loaders.cache`，来自 `--prefix=/usr/local`。

#### 10.2、第 2 层：`dlopen` 结构上不可能成功 ⚠️ 致命

**awesome 二进制没有 `.dynsym` 段**：

```sh
readelf -S awesome.pristine | grep -c "\.dynsym"   → 0
readelf -d awesome.pristine                        → There is no dynamic section in this file
```

**而 loader 的依赖是**：

```
libpixbufloader-xpm.so  DT_NEEDED:
  libgdk_pixbuf-2.0.so.0     ← 我们链的是 .a，磁盘上不存在
  libglib-2.0.so.0           ← 同上
  libgobject-2.0.so.0        ← 同上
  libc.so.6                  ← 同上
```

全静态链接时这四个 `.so.0` 都不在磁盘上 → `dlopen()` 第一步就失败。就算能打开，loader 里
`gdk_pixbuf_register_format` 这类未定义符号也**无处解析**——没有动态符号表就没有导出符号。

#### 10.3、第 3 层：ABI 版本不匹配

二进制 rodata 里现成的错误串：

```
Image-loading module %s does not export the proper interface; perhaps it's from a different gdk-pixbuf version?
```

不同发行版 gdk-pixbuf 小版本不同，就算前两层通了也会被拒。

#### 10.4、→ 撤回一·9 方向 1

**设 `GDK_PIXBUF_MODULE_FILE` 指向系统 cache 救不了。** 它只碰第 1 层，第 2 层是结构性的。

#### 10.5、意外发现：工具链里**没有 PNG / JPEG loader**

```sh
find / -iname '*pixbufloader*png*' -o -iname '*pixbufloader*jpeg*'   → 0 命中
```

cache 里注册的 12 种格式：`ani  bmp  gif  icns  ico  pnm  qtif  svg  tga  tiff  xbm  xpm`
——**没有 png，没有 jpeg**。而 PNG 才是最关键的（`background.png`、`submenu.png`、所有主题图标）。

所以就算第 2 层能绕过，PNG 照样坏。这条把「env 变量方案」彻底判死刑。

#### 10.6、完全静态化：能，而且比想象便宜

gdk-pixbuf 架构是 **core + 插件，core 里一个解码器都没有**——但插件机制可以整个绕开：

```c
// 1. 核心 API，不需要 loader
pixbuf = gdk_pixbuf_new(GDK_COLORSPACE_RGB, TRUE, 8, w, h, stride);
// 2. 自己解码（libpng 已静态链入）
// 3. memcpy 进 core 给的缓冲
guchar *p; unsigned int len;
gdk_pixbuf_get_pixels_with_length(pixbuf, &len);
```

**PNG 解码几乎免费**：libpng 1.6.37 已经在二进制里（pango 的依赖），`strings` 命中
`png_image_begin_read_from_file` / `png_do_rgb_to_gray` 那套新 API。

**JPEG 与 PNG 同批，不是第二批**：`/usr/lib/libjpeg.a`（libjpeg-turbo 2.1.2，787,628 B）就位，
`-ljpeg` 本来就在链接行里。

| 格式 | 工作量 |
| --- | --- |
| **PNG** | 几乎免费，libpng 1.6.37 已在二进制里，只需在 shim 接上 |
| **JPEG** | **与 PNG 同批**：`/usr/lib/libjpeg.a` 存在（libjpeg-turbo 2.1.2，含 AVX2/SSE2），`-ljpeg` 已在链接行，只需 shim 里真调 `jpeg_*` 符号 |
| **XPM** | ~200 行解析器（XPM 是纯文本，格式简单） |
| SVG | librsvg，本来就在遗留清单（`librsvg-2.0.a` 缺失） |

**⚠️ 当前二进制里 libjpeg 解码器其实是 0**：

```sh
strings awesome.pristine | grep -cE "Corrupt JPEG file|jpeg_std_error|Too few quantization tables"  → 0
strings /usr/lib/libjpeg.a  | grep -cE "同上"                                                          → 2
```

`-ljpeg` 被 `-Wl,--as-needed` 丢了——没有任何目标文件引用 `jpeg_*` 符号。`-ljpeg` 是 gdk-pixbuf
的 pkg-config 依赖报出来的，而 JPEG 解码代码在 loader `.so` 里，loader 没链入。
**这意味着 shim 一旦调用 `jpeg_*`，`--as-needed` 会自动把它保留**，不用改链接行。

**改动面**：`lib/vendor/lgishim_pixbuf.c:319` 的 `pixbuf_new_from_file()` 一个入口 + 一个解码分发层。
`lib/gears/surface.lua:59` 调用点不动，`draw.c:85 draw_surface_from_pixbuf()` 不动。

#### 10.7、方案对比

| 方案 | 可行性 | 说明 |
| --- | --- | --- |
| 设 env 指向系统 cache | ❌ | 第 2 层过不去 |
| 打包 loaders + 写自定义 cache | ❌ | `DT_NEEDED libgdk_pixbuf-2.0.so.0` 永远满足不了 |
| **shim 内自解码 + `gdk_pixbuf_new()` 填充** | ✅ | 真静态、跨发行版、不依赖目标机 |
| 把 loader 源码静态编译 + 手调 `install_module` | ⚠️ | 可行，但 loader 依赖的 libpng/libjpeg 也得静态，工作量不比上个大 |
| 改用 `cairo_image_surface_create_from_png` | ⚠️ | 返回值不是 GdkPixbuf，要改 `draw.c:85`，超出 shim 边界 |

这条链也解释了为什么**真机 XPM 报错**和**容器里跑不出图片**是同一类问题——工具链从源头就没装

#### 10.10、⚠️ 方法论教训：探测静态库别只用 `find`

判断「工具链里有没有某静态库」时，`docker exec <c> find / -name 'libx*.a'` 返回空**不能**
直接下结论——`find /` 会遍历 `/proc` `/sys` 等巨量目录，容易被截断或超时（本次就是这样误判了
`libjpeg.a` 不存在）。**改用链接测试定案**：

```sh
docker exec builder-awe sh -c 'cd /tmp && echo "int main(){return 0;}" > t.c && \
  gcc t.c -static -L/usr/lib -ljpeg -o t && echo LINK_OK'
```

以及用**库本体的标志性错误串**反向确认是否真被链入（比查符号表可靠，静态二进制是 stripped 的）：

```sh
strings bin | grep -c "Corrupt JPEG file"      # libjpeg 本体 = 2，awesome = 0 → 被 --as-needed 丢了
```

对照法很关键：同一个 grep 在已知存在的库里能命中，才说明搜索方法本身有效。

#### 12.2、同一份代码里「文件不存在」会报、「nil」不会

`lib/gears/surface.lua:101-111` 是整个分支的关口：

```lua
local function do_load_and_handle_errors(self, func)
    if type(self) == 'nil' then
        return get_default()                        -- ← nil 在这里就走了
    end
    local result, err = func(self, false)
    if result then
        return result
    end
    gdebug.print_error(debug.traceback(             -- ← 只有非 nil 且加载失败才有 traceback
        "Failed to load '" .. tostring(self) .. "': " .. tostring(err)))
    return get_default()
end
```

非 nil 的文件路径失败路径在 `surface.lua:58-62`：

```lua
if type(_surface) == "string" then

    if not pixbuf then
        return get_default(default), tostring(err)   -- err 回传 → :109 print_error → 有日志
    end
```

**只要 `wallpaper` 是 nil，就一定没有 traceback；只有给了路径但加载失败，才会有

#### 12.8.2a、"怎么判断背景色"——方法学（这一节是判据本身，别抄错了用）

#### 12.8.3、代码级根因（**⚠️ 2026-09-26 二次更正**：这一节的初稿写错了，见文末 12.8.8）

初稿（**结论部分错误，保留作历史**）：

> root.c:488/503 的 `luaA_root_wallpaper` 要 **lightuserdata**，而 lgishim 的 `push_obj`
> 推的是 **full userdata**，于是 `lua_touserdata` 拿到 `wrap*` 而非 `cairo_pattern_t*`，
> `cairo_set_source` 静默失败。

**这段说错了**——因为 `capi.root.wallpaper` 根本不是 C 函数 `luaA_root_wallpaper`，
而是 `lib/awful/_compat.lua:65-79` 定义的 **Lua shim**（详见 12.8.8）。shim 会自己再调
一次 `root._wallpaper(...)`。真正的根因是 **lgishim_cairo.c 把 `_native` 注册成 metatable
上的 C closure，`pattern._native`（无括号）拿到的是函数本身而不是 lightuserdata**——这才
导致 shim 把 `m_native` 这个 Lua closure 塞给了 C 层。`lua_touserdata(closure) == NULL`
才是"静默失败"的直接来源。

**结论方向（"上传静默失败 → 壁纸纯黑 → 抓像素才能定位"）没变**，只是"传的是什么错"
需要按 12.8.8 的调用链来看。

#### 12.8.4、为什么这个 bug 隐形到极致（也是它难查的原因）

`root.c:488/503`：

```c
 * @param pattern A cairo pattern as light userdata
...
cairo_pattern_t *pattern = (cairo_pattern_t *)lua_touserdata(L, -1);
```

注释白纸黑字要 **lightuserdata**，而 lgishim 的 `push_obj`（`lib/vendor/lgishim_cairo.c:158-173`）
推的是 **full userdata**：

```c
w = (wrap *)lua_newuserdata(L, sizeof(wrap));   /* :167  wrap = { ptr, destroy, cls } */
w->p = p;
```

于是 `lua_touserdata(L,-1)` 拿到的是 **`wrap*`**，不是 `cairo_pattern_t*`。shim 里正确的
解包方式是 `chk()`（`:147-155` → `w->p`），它对外暴露成 `_native`（`m_native` `:473-481`，
注册在 `:615-616`）。仓库里已有同样用法的先例：`lib/gears/surface.lua:63`
`capi.awesome.pixbuf_to_surface(pixbuf._native, ...)`。

传错之后 `cairo_set_source(cr, pattern)` 拿到垃圾指针，**cairo 只置错误状态、不抛异常**。

#### 12.8.4b、为什么这个 bug 隐形到极致（第二层：绘制链上没有任何错误出口）

#### 12.8.7、方法论教训（这次最值钱的一条）

**「API 返回 true / 返回了个对象」在这套构建里等于零证据。** lgishim 把 lgi 的异常语义
全换成了「返回 false 或置错误状态」，而 `root_set_wallpaper` 连状态都不查——所以整个壁纸
子系统**没有任何 Lua 可见的失败信号**。

以后凡是「画不出东西」这类问题，**第一判据必须是抓像素**（Xvfb + `import -window root` /
`scrot` + 直方图），不是打日志、不是回读 API。前几轮一直在 Lua 侧找证据，方向就错了。

另外记一条坑：`/ext/tmp` 挂载到容器**不一致**——host 上刚写的文件，容器里可能只看到前
几行或根本不存在。往 builder 里跑脚本要用 `docker exec -i ... sh -s < 文件` 走 stdin，或者
`base64 -w0` 走命令行参数；取结果用 `docker cp` 拉回来。`docker exec` 里起后台进程会挂住，
要 `nohup ... & echo STARTED` 脱开。

#### 12.8.8、更深的真因（用户追问"改 Lua 脚本还是 vendor 层合适？官方 Lua 脚本原本没问题吧"——命中的正是这里）

用户 2026-09-26 追问："**修复 lua 脚本而不是 vendor 层合适吗？lua 脚本原官方版本是没问题的吧，需要考虑与官方版本的脚本兼容。**"

**用户是对的**。12.8.3 初稿把根因归给"lgishim full userdata 传 C"，那是错的。重新捋一遍
调用链，**真·真因其实在 vendor 层的 `_native` 设计选择**：

**调用链全貌**（`capi.root.wallpaper(pattern)` 走到的完整路径）：
```
lib/awful/wallpaper.lua:373   capi.root.wallpaper(pattern)
      ↓  ← capi.root.wallpaper 不是 C 函数！
lib/awful/_compat.lua:65      function root.wallpaper(pattern)
      ↓  官方上游 2016 年就为 LGI-ified surface 加了这一层 shim
lib/awful/_compat.lua:71      local err = pcall(function() return pattern._native end)
lib/awful/_compat.lua:76      return root._wallpaper(pattern._native)   -- 期望 _native 直接是 lightuserdata
      ↓
root.c:503                    cairo_pattern_t *pattern = (cairo_pattern_t *)lua_touserdata(L, -1);
```

**`_compat.lua` 是官方上游脚本，一行都没改**（git log：`b0a2d82d compat: Do not require
to pass pattern._native to the wallpaper`，2016 年）。它假定 `pattern._native` 是
**lightuserdata**（直接就是 raw pointer），这是 **真 LGI 的语义**。

**为什么我们构建里不成立**：
```
lib/vendor/lgishim_cairo.c:615-616
    lua_pushcfunction(L, m_native);
    lua_setfield(L, -2, "_native");
```
`_native` 被注册成 **metatable 上的 C closure**。访问 `pattern._native` 走 `m_index`
的 fallback 分支（`:438-447`），把 `_native` 字段查出来后原样返回——**返回的是 `m_native`
这个函数，不是函数调用后的结果**。

对比同 vendor 目录下另外两个 shim：
- `lib/vendor/lgishim_pixbuf.c:157, 499, 516` → `_native` 注册在 **pg（property getter）** 表里，
  `m_index` 的 pg 分支（`:403-413`）**自动以 obj 为 self 调用 getter 并返回结果**，所以
  `pixbuf._native == lightuserdata`（GdkPixbuf*）。
- `lib/vendor/lgishim_gobject.c:620-632` → 同样把 `_native` 放 NATIVE_PG，注释明确写：
  > "A metatable field would hand back the closure itself, and `lua_touserdata()` on a
  > Lua function yields NULL."

cairo / pango / glib / gio 这四个 shim 把 `_native` 放 metatable 是**设计选择错误**，跟
pixbuf/gobject 不一致，也不符合真 LGI 语义。**上游 Lua 期望它 auto-invoke，我们 vendor
没提供这个行为**。

**"full userdata vs lightuserdata"初稿为什么错**：`root.c:503` 收的确不是 lgishim 的
`wrap*` full userdata，而是 `_compat` shim 塞进去的 **`m_native` 这个 Lua closure**——
`lua_touserdata(L, closure) == NULL` 才是"静默失败"的直接来源。**根因层级完全不一样**。

**为什么我的补丁 `pattern:_native()` 恰好能修**：
```
capi.root.wallpaper(pattern:_native())
             ↑ pattern:_native() 显式调用 m_native(pattern) → 返回 lightuserdata
capi.root.wallpaper(lightuserdatum)
  ↓ _compat shim 运行
pcall(function() return lightuserdatum._native end)
  ↑ lightuserdata 没有 metatable，访问 .field 抛错 → pcall 返回 false → err = false
if err and not root._write_string then ... else root._wallpaper(pattern) end
  ↑ 走 else 分支，把 raw lightuserdata 直传给 C → root.c 拿到正确指针 → 壁纸生效
```
**这个修复是"歪打正着"**：靠"pcall 在 lightuserdata 上失败"这个副作用把 shim 逼到了
else 分支。**功能上是对的，但机制上很脆弱**——任何依赖"pcall 在 lightuserdata 上必失败"
的地方，一旦 shim 层加个 metatable 都会崩。

**修法选项**：

| | 修法 | 代价 | 兼容性 |
| --- | --- | --- | --- |
| **A（当前提交）** | 改 `awful/wallpaper.lua:373` → `pattern:_native()` | Lua 侧 1 行，不用重编 | 只修 wallpaper，wibox shape 等类似隐患还在；偏离上游脚本 1 行 |
| **B（推荐）** | 改 `lgishim_cairo.c`：把 `_native` 从 metatable 移到 pg，加 `NATIVE_PG[]`；然后把 `awful/wallpaper.lua:373` 改回上游原样 `capi.root.wallpaper(pattern)` | C 侧重编（走 builder-awe），diff ~15 行 | 100% 兼容上游脚本；`wibox.shape_bounding = img._native` / `gears.surface.apply_shape_bounding` / `snap` / `client/shape` 这些**同类隐患也一并修好** |
| **C** | 只改 `lgishim_cairo.c`，不动 `awful/wallpaper.lua` 的当前修复 | 重编 + 补丁保留 | 双层冗余，能跑但代码里留了个"为什么这里要 `:_native()`"的疑问 |

**推荐 B**：这是**唯一让 vendor 与上游 `_compat.lua` 语义一致**的修法。上游 `_compat.lua`
已经为 LGI-ified surface 准备好了处理，我们的 vendor 层没把 `_native` 暴露成真 LGI 那样
的 auto-invoked 属性，导致官方 shim 拿不到 lightuserdata 就"静默失败"了。**上游 Lua 脚本
完全没问题，问题全在 vendor**。

**同类隐患（12.8.6 已列的 P1，现在有更具体的定位）**：
- `lib/wibox/init.lua:133, 152, 173` `self.shape_bounding = img._native`（img 是 cairo.ImageSurface）
- `lib/gears/surface.lua:227` `draw.shape_bounding = img._native`
- `lib/awful/mouse/snap.lua:70`
- `lib/awful/client/shape.lua:105, 117`

这些位置传的是 cairo.Surface 的 `._native`（无括号），当前构建下**也是把 `m_native` 函数
当 native 传**——`lua_touserdata(closure) == NULL`，X 侧 shape 静默失效。**用户目前跑
起来没崩溃大概率是因为这些路径触发频率低，或 X 侧拿到 NULL shape 时走 fallback**——
不是"没事"，是"侥幸"。修法 B 一并解决。

 **当前状态**：`bfe0b7fc` 已推（修法 A，1 行改动，Lua 解释执行），**功能上壁纸已修复，

#### 12.8.11、gdk-pixbuf 自解码落地：PNG / JPEG / XPM（`lgishim_pixbuf.c` +536 / -2）

 背景：一·10 已经把 `gdk_pixbuf_new_from_file` 在静态构建里的三层失败定案了
 （loader module 靠动态加载，静态构建拿不到），结论是"要么自解码、要么没图"。
 用户本轮令"给做了"，所以 `lgishim_pixbuf.c` 里 `pixbuf_new_from_file` 走
 **magic-byte 分发 + 自解码**：

 - **PNG**：libpng 简化 API（`png_image_begin_read_from_file` / `_read` / `_free`），
   自带 stride / filter 处理，直接得到 `CAIRO_FORMAT_ARGB32` 像素。
 - **JPEG**：libjpeg 标准 API（`jpeg_read_header` → `jpeg_read_scanlines`），
   RGB → ARGB32 打包。
 - **XPM**：**自写解析器**（不能复用 `gdk_pixbuf_new_from_xpm_data`——它内部同样走
   loader module 动态加载，静态构建里必然失败）。支持 1-bit / 8-bit 深度、
   space 当透明色、`c #RRGGBB` 颜色表、`rgb:` / `rgba:` 前缀、cpp>1 多字符 key。
 - 未知格式回退 `gdk_pixbuf_new_from_file`（保持上游行为，不吞掉错误）。

 顺带修掉自写解析器里的一个真 bug：`sscanf("%x", ...)` 直接写进 `unsigned char*`
 会按 32 位写、把相邻的 width 冲成 0。改成先写 `unsigned int` 临时量再截断。

 **验证（宿主 + Xvfb，`pix._native` 判成功，不再用 `pix:get_width()`——pixbuf shim
 只有 `new` / `new_from_file` / `finish`，没有 `get_width`）**：

 - 文件不存在 / 未知扩展名 → 优雅返回 nil（不崩）

#### 13.6、编译 rsvg 的坑清单（2026-09-27 实测，openbox 文档四.8 同款）

1. **libcroco 的 pc 文件名是 `libcroco.pc` 不是 `libcroco-0.6.pc`** → librsvg configure 报
   `Package 'libcroco-0.6', required by 'virtual:world', not found`（`checking for
   LIBRSVG... no`）。解决：`cp /tmp/libcroco/libcroco.pc
   /usr/local/lib/pkgconfig/libcroco-0.6.pc`（内容正确，只差文件名；pkg-config 按
   **文件名**（去 `.pc`）匹配包名）。
2. **librsvg `make install` 假通过失败**：`make[1]: *** [install-recursive] Error 1`——
   install 先 build all，链测试程序缺 `-lexpat -lgmodule -ljpeg`（静态闭包没展开）。
   但 build.sh 框架照打 `err 0, pass`（deps 阶段无质量门，openbox 文档记过同款）——
   **别信 `err 0, pass`，看 `.libs/librsvg-2.a` 有没有出**。库本体已出（432,214 B），
   绕过 install 手工装。
3. **手工安装要装全四件**：
   - `.a`：`.libs/librsvg-2.a → /usr/local/lib/librsvg-2.a`
   - 头文件：`/usr/local/include/librsvg-2.0/librsvg/{rsvg.h, librsvg-enum-types.h,
     librsvg-features.h, rsvg-cairo.h}`——`rsvg.h` 用**同目录 quoted include**
     引后三个，少一个都编不过
   - pc：`/tmp/librsvg/librsvg-2.0.pc → /usr/local/lib/pkgconfig/`（prefix=/usr/local 已对）
   - **`.la` 别删**（openbox 同款）：删了 libtool 展开不了 `dependency_libs` →
     `pango_cairo_*` 8 个符号 undefined；手工安装保留 `/usr/local/lib/libcroco-0.6.la`
4. **librsvg-2.0.pc 的 `Requires` 只有 glib/gio/gdk-pixbuf/cairo，没有 libcroco /
   libxml2 / pangocairo** → 链接必须手工补 `-l:libcroco-0.6.a -lxml2 -lexpat`
   （`pkg-config --static --libs librsvg-2.0` 也不给）；`-lgmodule -lmount -lblkid
   -lpixman -lpangocairo` 我们链接行已有。
5. **前置 intltool**：libcroco autogen 要 `intltoolize`（本容器 `/usr/bin/intltoolize`
   已有；openbox 构建是 `apk add intltool` 补的）。
6. **验证先于重编**：写最小 C 测试（`rsvg_handle_new_from_file → get_dimensions →
   render_cairo → write_to_png`）先在容器里静态链接跑通，再动 awesome 构建，避免在
   10MB 链接行里迭代；测试 SVG 要容器里真实存在的文件（builder 里没有 Ubuntu 图标，
   用 `/tmp/min.svg` 自造）。
